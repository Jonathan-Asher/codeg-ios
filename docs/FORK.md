# Codeg Plus: fork notes

This repository is a fork of [xintaofei/codeg-ios](https://github.com/xintaofei/codeg-ios)
(Apache-2.0), built and shipped through TestFlight by Jonathan Ashurov as
**Codeg Plus**. Upstream is largely frozen, with several useful fixes waiting
in open pull requests. The fork carries those fixes and its own app identity, so it
installs next to the upstream app. Features for Jonathan's own codeg server,
push notifications and on-device voice (read aloud and voice typing), are
added here.

`LICENSE` is kept as upstream ships it. `THIRD_PARTY_NOTICES.md` keeps
upstream's entries and adds the fork's own dependencies at the end.
`NOTICE` keeps upstream's attribution and adds a line saying this is a
modified version. This document and the git history record what changed, as
Apache-2.0 section 4(b) asks.

## App identity

Everything that names the app lives in [`Config/Identity.xcconfig`](../Config/Identity.xcconfig):

| Setting              | Value              | Used for                                                |
| -------------------- | ------------------ | ------------------------------------------------------- |
| `CODEG_DISPLAY_NAME` | `Codeg Plus`       | `CFBundleDisplayName`, permission strings, in-app title |
| `CODEG_BUNDLE_ID`    | `io.ashurov.codeg` | `PRODUCT_BUNDLE_IDENTIFIER`, URL type name              |
| `CODEG_URL_SCHEME`   | `codegplus`        | Registered URL scheme; deep links are `codegplus://…`   |

The Apple Developer team, `3L92BZK46V`, is committed in
[`Config/Signing.xcconfig`](../Config/Signing.xcconfig). It is not a secret.
An ignored `Config/Signing.local.xcconfig` can still override it.

To rename the app (for example, if App Store Connect rejects "Codeg Plus"),
change `CODEG_DISPLAY_NAME` and run `xcodegen generate`. The App Store name
itself is set on the App Store Connect app record.

`Info.plist` also declares `ITSAppUsesNonExemptEncryption = NO`, because the app
only uses the system's HTTPS/TLS. That skips the export-compliance question on
every upload.

## Push notifications

[`CodegiOS/CodegiOS.entitlements`](../CodegiOS/CodegiOS.entitlements) is
generated by xcodegen from `project.yml` and contains:

- `aps-environment = development`. When an archive is exported for App Store
  Connect, Xcode re-signs it with the distribution profile, which sets this to
  `production` for TestFlight and App Store builds.
- `com.apple.developer.usernotifications.time-sensitive = true`

The app talks to codeg's push backend (`docs/ios-push.md` in the codeg repo,
branch `fork/solution-plan`). `App/PushRegistration.swift` does the work:

- **Permission.** Asked right after a server is added, on launch when servers
  already exist and the question was never asked (an install that predates
  push), or from Settings › Notifications. Never on a first launch with no
  server. It asks for alerts, sounds and badges. Time-sensitive delivery needs
  no option of its own: it comes from the entitlement, and iOS shows its own
  "Time Sensitive Notifications" switch for the app.
- **Registration.** `registerForRemoteNotifications()`, then
  `POST /api/register_push_device {token, environment, bundleId, name,
  platform: "ios"}` to every saved server, on every launch and whenever the
  token changes (the old token is unregistered first). Each server's
  `server_id` and this phone's device id are kept in `PushServerIndex`
  (UserDefaults).
- **Environment.** Read from the embedded provisioning profile: a development
  profile (a build run from Xcode) means `sandbox`; TestFlight and App Store
  builds carry none or a distribution one, which means `production`. Without a
  profile (the simulator) the `DEBUG` compile flag decides.
- **Unregistering.** Removing a server calls `unregister_push_device {token}`
  on it. Turning push off in the app, or denying notifications in iOS
  Settings, unregisters from every server: a server that believes the phone
  took a critical alert skips its chat-channel fallback.
- **Categories and actions.** `CODEG_CRITICAL` (Acknowledge, Snooze 15 min,
  Open), `CODEG_PERMISSION` (Approve, Open) and `CODEG_SESSION` (Open).
  Acknowledge, Snooze and Approve run in the background
  (`ack_critical_session`, `snooze_critical_session`,
  `acp_respond_permission` with `approve_option_id`); Approve needs the device
  unlocked. The server is picked by the payload's `server_id`. An approval that
  fails (answered elsewhere, connection gone) posts an "Already handled" local
  notification that opens the session.
- **Opening.** A tap or Open switches to the push's server and opens
  `conversation_id` with a fresh stack, at the latest message. Opening a
  critical session also acknowledges it, as the desktop does.
- **Foreground.** Pushes show as banners, except one about the session that is
  on screen. Notification Center groups them by `thread-id` (one group per
  session).
- **Presence.** While a session is on screen and the app is active,
  `Networking/SessionPresence.swift` keeps an event socket open with the extra
  `codeg-client.ios` subprotocol and sends
  `{"action":"presence","visible":true,"focused":true,"idle_secs":0,
  "conversation_ids":[id]}` on connect, on change and every 25 s, then
  `visible: false` when the session closes or the app leaves the foreground.
  The server never counts a phone as someone at the desk, but nothing is
  pushed about the session the phone shows. Every other event socket also
  declares `codeg-client.ios` and reports nothing, so it never counts as
  looking.
- **Settings › Notifications** shows the iOS permission, the app-level switch
  and, per saved server, this phone's device preferences on that server (turn
  finished and needs you: always / only when away / off; critical alerts;
  errors) through `list_push_devices` / `update_push_device_prefs`, plus "Send
  test push" (`send_test_push`).

## Session features from the codeg fork

These need Jonathan's codeg server (`fork/solution-plan`). Against an upstream
server they degrade quietly: the new fields are absent and the old behaviour
remains.

- **What a session is doing.** `Models/SessionActivity.swift` ports
  `deriveSessionActivity` (`src/lib/session-activity.ts`) and the held-turn
  rules of `src/lib/background-idle.ts`: Working, Needs you, Idle, Interrupted,
  "Idle — N background tasks running", "Paused — limit resets at … (in …)",
  Connecting… (with the `attach_progress` phase) and Couldn't connect. Inputs:
  the summary's `turn_state` and `limit_pause`, the attention snapshot
  (`list_conversation_attention`, refreshed with the session list), and, on
  the open session, its own live connection (`awaiting_background`,
  `background_outstanding`). Session rows and the session title show it.
- **Insert into the current turn.** While a turn runs, the send button offers
  "Insert into current turn" when the attach snapshot says
  `native_steering_available`. It calls `submit_session_feedback
  {connectionId, text, blocks?}`; a "no active turn" rejection sends the
  message as a normal prompt. Without steering, or with "Send when this turn
  ends", the message waits in a queue above the composer (send now, edit,
  remove) and goes out when the turn finishes.
- **Background work.** While the turn is held only for background tasks
  (`awaiting_background`) and steering is available, send delivers at once, and
  the queue drains into the held turn one message at a time.
- **Continue.** After an agent reply, with an empty composer, a Continue chip
  sends `continue` (the fork's `CONTINUE_PROMPT`). User turns that are exactly
  `continue`, the resume-after-restart prompt, or the continue-after-limit-reset
  prompt render as slim "▶ Continued", "Resumed after restart" and "Continued
  after limit reset" dividers.
- **Model, effort and mode.** Session Details lists the summary's
  `selector_state`. Its config ids (`reasoning_effort`, …) are read from the
  raw JSON, because the shared decoder's snake_case conversion also rewrites
  dictionary keys.
- **New events** decode instead of being dropped: `attach_progress`,
  `awaiting_background`, `background_activity`, `feedback_submitted`,
  `feedback_consumed`.

## Read aloud (BlueTTS)

`Packages/BlueTTSKit` is Jonathan's on-device Hebrew + English TTS package
(BlueTTS 2.5 + RenikudPlus, ONNX Runtime 1.30.0), vendored with git subtree.
Update it with:

```bash
git subtree pull --prefix Packages/BlueTTSKit <path-or-url-of-codeg-voice/BlueTTSKit> main --squash
```

- **Models.** The ~575 MB of model files are not bundled.
  `Features/Voice/VoiceModelStore.swift` ports `scripts/fetch-models.sh`: the
  same pinned files and sha256 list, downloaded by a background `URLSession`
  into Application Support (excluded from backups), resumable, each file
  checked before it is moved into place. It starts from Settings › Voice, or
  from the first Read aloud, and asks first because of the size.
- **Playback.** "Read" under an agent reply (next to Copy) streams
  `synthesizeStream` chunks into an `AVAudioPlayerNode`, with the `.playback`
  audio session in `.spokenAudio` mode. The `audio` background mode keeps it
  reading with the screen locked; Now Playing shows the reply, and the lock
  screen can pause, resume and stop it.
- **Text.** The prose is read with the Markdown stripped. Fenced code and tool
  output are skipped unless Settings › Voice turns them on.
- **Fallback.** Until the model is downloaded, `AVSpeechSynthesizer` reads with
  the Hebrew (Carmit) or English system voice per span of text.

### Licences: read before any public release

- BlueTTSKit is MIT (`Packages/BlueTTSKit/LICENSE`).
- **BlueTTSEspeak, which the app links for English phonemes inside Hebrew
  text, is espeak-ng: GPL-3.0-or-later.** That makes the app binary a GPL-3
  work. It is fine for Jonathan's own TestFlight builds, but it must be
  replaced (with another `EnglishPhonemizer`, for example a CMU-dictionary +

  public App Store release.
- The BlueTTS 2.5 weights declare no licence; confirm with their author before
  a public release.

## Voice typing (on-device whisper)

The mic in the message bar transcribes speech on the iPhone. Nothing is sent
to a server, and Apple's `SFSpeechRecognizer` is not used, so the app needs
only `NSMicrophoneUsageDescription`.

### Engine: whisper.cpp

`Packages/WhisperCpp` is a binary target for the official whisper.cpp v1.9.1
XCFramework (MIT), pinned by URL and checksum. It is a dynamic framework that
the app binary loads, so `scripts/archive.sh` keeps it in the bundle. The app
uses it with `import whisper`. Everything goes through the `SpeechToText`
protocol (`Features/Dictation/SpeechToText.swift`), and `WhisperCppEngine` is
the only implementation, so the engine can be replaced later.

Why not WhisperKit: it needs ivrit.ai's model converted to Core ML with
`whisperkittools` (PyTorch and coremltools on a large model). That is not
practical on the 16 GB build box, which has no Xcode. whisper.cpp reads
ivrit.ai's published ggml weights directly, and Speakly already uses the same
model, VAD and settings on the Mac. The tradeoff is speed. WhisperKit runs
large-v3-turbo on the Neural Engine at about 6–9× real time on an iPhone 16/17
Pro. whisper.cpp runs on the GPU through Metal, and nobody has benchmarked it
on an iPhone. The XCFramework is built with Core ML support
(`WHISPER : COREML = 1`). A future `ggml-ivrit-large-v3-turbo-q8_0-encoder.mlmodelc`
placed next to the weights would move the encoder to the Neural Engine without
changing the engine code, but producing that file needs the same Python
conversion as WhisperKit.

Decode settings follow Speakly: greedy decoding (`best_of` 1), the language
forced, `no_context`, `suppress_nst`, flash attention, up to 4 CPU threads,
Metal on a device and the CPU in the simulator. Timestamp tokens stay on, as in
Speakly and whisper-cli. With them off, English speech came out transliterated
or translated into Hebrew. Speakly's scaled `audio_ctx` (encode only the length
of the clip) was measured and rejected: it cut decode time by 28% but raised
FLEURS WER from 23.7% to 40%.

### Pipeline

1. **Record.** `DictationRecorder` uses `AVAudioEngine` and converts the input
   to 16 kHz mono Float32. The meter shows input level from -55 to 0 dBFS, and
   a recording stops at 5 minutes.
2. **Trim.** Silero VAD v5.1.2 (the ggml model, through whisper.cpp's VAD API,
   on the CPU) gives one speech probability per 32 ms frame. `VADGate` is a
   port of Speakly's gate (`crates/engine/src/vad/gate.rs`):
   - a segment opens at p ≥ 0.6 held for 2 frames;
   - it closes after 300 ms below 0.35;
   - speech shorter than 250 ms is dropped;
   - a segment is force-split at 25 s.

   `DictationTrim.plan` keeps everything from the first to the last speech
   with 150 ms of padding. A recording shorter than 0.4 s is a mis-tap. With
   no speech, or less than 250 ms, nothing is decoded, which avoids whisper's
   hallucinations on silence. If the VAD model fails to load, the whole
   recording is decoded.
3. **Decode.** There is one decode over the trimmed audio, as in Speakly's
   dictation. Output that is only non-speech markers (`[BLANK_AUDIO]`,
   `(מוזיקה)`) is dropped.
4. **Insert.** `DictationText.insert` puts the text at the field's cursor, or
   replaces the selection, using the iOS 18 `TextField(text:selection:)`
   binding. It adds a space where the transcript would touch a word, and the
   cursor ends after the inserted text. With "Send" on, the message is then
   sent. While a turn runs, it is delivered at once when the turn is held only
   for background work, and queued otherwise.

The model starts loading when recording starts, so the load overlaps the
speech. It is unloaded after 3 minutes idle, on a memory warning, and when the
app goes to the background. A loaded q8_0 model takes about 1.1 GB. iOS doesn't
let a background app use the GPU. If the app goes to the background during a
recording, the recording ends and its decode waits until the app is active
again. A decode that is already running is cancelled and run again then.

### UX

- **Mic button**, next to Send. Tap to start and tap again to stop, or hold to
  talk and let go to stop (a press longer than 0.35 s counts as a hold).
  VoiceOver activation toggles. While recording, the button turns into a red
  stop button. While transcribing, it shows a spinner.
- **Recording strip** above the field: a pulsing dot, the elapsed time, a live
  level meter, a **Send** switch (send right after transcribing, remembered),
  and cancel.
- **Settings › Voice › Voice Typing**: the model download (download, pause,
  resume, delete, progress), Language, "Send right after transcribing" and
  "Use the session context".
- **Without the model**, tapping the mic offers the download (875 MB) and
  points to the mic key on the iOS keyboard, Apple's own dictation. During the
  download, a notice shows the progress. If the microphone is denied, a notice
  says where to allow it.
- **Audio session.** The session is set to `.playAndRecord` only while
  recording, and Bluetooth HFP is allowed so AirPods work as the microphone.
  Any reply being read aloud is stopped first. On stop, the session is
  deactivated with `.notifyOthersOnDeactivation`, and Read aloud sets
  `.playback` again the next time it starts. A call or Siri interruption, or a
  route change that stops the engine, ends the recording and transcribes it.

### Language setting

| Setting | Model | Notes |
| ------- | ----- | ----- |
| Hebrew (default) | ivrit.ai turbo q8_0, `he` forced | English terms come out as the model writes them, often transliterated (ריבייס, טייפ סקריפט); the prompt keeps more of them in Latin letters |
| English | same model, `en` forced | WER 17.6% on the five English clips; the Hebrew-mode prompt keeps English speech English too (19.6%) |
| Detect automatically | stock large-v3-turbo q5_0 (574 MB, separate download), `auto` | Detection works (25/25 Hebrew, 5/5 English). Hebrew is much weaker (FLEURS WER 33.6% vs 23.7%), and 3 of 8 Hebrew sentences full of code terms were detected as English and came out as English gibberish. ivrit.ai's model card says its language detection was degraded by the
fine-tune. Measured here, it called every English clip Hebrew (p ≈ 1.0), so
Auto does not use it.

| - | - | - | - |

q8_0 transcribes as f16 does, at about half the size, and has the fastest
encoder of the three on the M1. q5_0 saves 300 MB but changes up to 8% of the
words. The test clips are synthetic, except FLEURS, so the Carmit and BlueTTS
WERs mostly measure how the voices pronounce English terms. Use them to
compare models, not as absolute accuracy. Mac timings only rank the models.
Speed on an iPhone has not been measured.

- **Source**: `ivrit-ai/whisper-large-v3-turbo-ggml` `ggml-model.bin`, sha256
  `c8090411…8641b1`, Apache-2.0 (checked on the model card and the base
  model's card). It was quantized with `whisper-quantize … q8_0` from
  whisper.cpp v1.9.1. As a check of the tool, the same command reproduced
  ggerganov's published `ggml-large-v3-turbo-q5_0.bin` byte for byte.
- **Hosting**: release
  [`models-v1`](https://github.com/Jonathan-Asher/codeg-ios/releases/tag/models-v1)
  of this repository, with the ivrit.ai model, the stock multilingual q5_0,
  Silero VAD, `stt-models.json`, `SHA256SUMS`, `NOTICE.txt` (what was changed,
  as Apache-2.0 §4(b) requires) and the Apache-2.0 text. GitHub serves byte
  ranges with an ETag, so downloads resume.
- **Manifest**: `CodegiOS/Resources/stt-models.json` is the same file as the
  release's `stt-models.json`. The app trusts only its bundled copy, so a file
  is moved into place only when its size and sha256 match.
- **Download**: `ModelPackStore` (`Features/Voice/ModelPackStore.swift`) is
  the BlueTTS downloader, now shared by both features. It uses a background
  `URLSession` per model and resume data on disk, and checks each file's
  sha256 before moving it into `Application Support/SpeechToText/<model id>`,
  which is excluded from backups.
- **New model version**: publish a `models-v2` release, update
  `stt-models.json` in both places and bump nothing else. Files with a new name
  or checksum download again.

## CI

[`.github/workflows/ios.yml`](../.github/workflows/ios.yml)

- **`test`** runs the `CodegiOSTests` unit tests (session activity, push
  payload routing, Markdown-to-speech text, the fork's JSON fields) on an
  iPhone simulator, in parallel with `build`.
- **`build`** runs on every push and pull request on GitHub-hosted `macos-26`
  with its default Xcode. It runs `brew install xcodegen`, `xcodegen generate`,
  then an unsigned `xcodebuild build` for `generic/platform=iOS Simulator`.
  Finally it checks that the built `Info.plist` carries the fork's bundle id,
  name and URL scheme.
- **`testflight`** archives and uploads to App Store Connect with cloud-managed
  signing, through [`scripts/archive.sh`](../scripts/archive.sh). That is the
  same archive, export and `altool` upload that `scripts/release.sh --archive`
  uses. It runs only on a manual dispatch with the `testflight` box ticked, and
  only when the repository variable `TESTFLIGHT_ENABLED` is `true`.

### Turning on the TestFlight job

1. Create an App Store Connect API key (Users and Access → Integrations →
   Team Keys) with the **Admin** role. Cloud-managed signing has to create
   certificates and profiles, which a lower role cannot.
2. Add three repository secrets:
   - `ASC_KEY_ID`: the key ID;
   - `ASC_ISSUER_ID`: the issuer ID;
   - `ASC_KEY_P8`: the contents of `AuthKey_<ID>.p8`, raw or base64-encoded.
3. Set the repository variable `TESTFLIGHT_ENABLED` to `true`.
4. Go to Actions → iOS → Run workflow and tick **testflight**. The build number
   defaults to the run number, and the `build_number` input overrides it. Each
   upload needs a build number higher than the last upload for that version.

On an ephemeral GitHub-hosted runner, xcodebuild has no signing identity. The
archive step therefore creates a new Apple Development certificate through the
API key on every run. Export signs with Apple's cloud-managed distribution
certificate. Expect certificates named "Created via API" to pile up in the
developer account, and revoke them from time to time. The self-hosted option
below avoids this.

### Alternative: Jonathan's self-hosted Mac runner

The same job can run on Jonathan's Mac, so the API key never leaves it:

1. Register a runner for this repository on the Mac (Settings → Actions →
   Runners), with an extra label such as `codeg-ios-release`.
2. Keep the key at `~/.appstoreconnect/private_keys/AuthKey_<ID>.p8` on the
   Mac. Store `ASC_KEY_ID` and `ASC_ISSUER_ID` as repository variables; they
   are not secret. No `ASC_KEY_P8` secret is needed.
3. In the `testflight` job:
   - set `runs-on: [self-hosted, macOS, codeg-ios-release]`;
   - read the IDs from `vars.` instead of `secrets.`;
   - replace the "Install the App Store Connect API key" step with
     `echo "ASC_KEY_PATH=$HOME/.appstoreconnect/private_keys/AuthKey_${ASC_KEY_ID}.p8" >> "$GITHUB_ENV"`;
   - drop the final "Remove the API key" step, because it would delete the
     Mac's key.

The development certificate then stays in the Mac's login keychain between
runs. The Mac must have the iOS platform and the Metal toolchain installed for
its Xcode (`xcodebuild -downloadComponent MetalToolchain`). The repository is
public, so the self-hosted label must stay on this manual-dispatch-only job.
Pull requests from forks must never get a self-hosted runner.

## Staying in sync with upstream

```bash
git remote add upstream https://github.com/xintaofei/codeg-ios.git
git fetch upstream
git merge upstream/main          # or cherry-pick individual commits
# Fetch an open upstream PR:
git fetch upstream pull/<n>/head:pr-<n>
```

Record anything you take from upstream in the table above.
