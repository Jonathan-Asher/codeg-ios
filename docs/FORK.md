# Codeg Plus: fork notes

This repository is a fork of [xintaofei/codeg-ios](https://github.com/xintaofei/codeg-ios)
(Apache-2.0), built and shipped through TestFlight by Jonathan Ashurov as
**Codeg Plus**. Upstream is largely frozen, with several useful fixes waiting
in open pull requests. The fork carries those fixes and its own app identity, so it
installs next to the upstream app. Features for Jonathan's own codeg server,
push notifications, on-device voice (read aloud and voice typing, with
clean-up and translation through the codeg server), Camera Control to
talk, and the pictures, videos, audio and documents a session refers to, are
added here.

`LICENSE` is kept as upstream ships it. `THIRD_PARTY_NOTICES.md` keeps
upstream's entries and adds the fork's own dependencies at the end.
`NOTICE` keeps upstream's attribution and adds a line saying this is a
modified version. This document and the git history record what changed, as
Apache-2.0 section 4(b) asks.

## App identity

Everything that names the app lives in [`Config/Identity.xcconfig`](../Config/Identity.xcconfig):

| Setting              | Value              | Used for                                                |
| -------------------- | ------------------ | ------------------------------------------------------- |
| `CODEG_DISPLAY_NAME` | `Codeg Plus`       | `CFBundleDisplayName`, permission strings, in-app title |
| `CODEG_BUNDLE_ID`    | `io.ashurov.codeg` | `PRODUCT_BUNDLE_IDENTIFIER`, URL type name              |
| `CODEG_URL_SCHEME`   | `codegplus`        | Registered URL scheme; deep links are `codegplus://…`   |

The Apple Developer team, `3L92BZK46V`, is committed in
[`Config/Signing.xcconfig`](../Config/Signing.xcconfig). It is not a secret.
An ignored `Config/Signing.local.xcconfig` can still override it.

To rename the app (for example, if App Store Connect rejects "Codeg Plus"),
change `CODEG_DISPLAY_NAME` and run `xcodegen generate`. The App Store name
itself is set on the App Store Connect app record.

`Info.plist` also declares `ITSAppUsesNonExemptEncryption = NO`, because the app
only uses the system's HTTPS/TLS. That skips the export-compliance question on
every upload.

## Push notifications

[`CodegiOS/CodegiOS.entitlements`](../CodegiOS/CodegiOS.entitlements) is
generated by xcodegen from `project.yml` and contains:

- `aps-environment = development`. When an archive is exported for App Store
  Connect, Xcode re-signs it with the distribution profile, which sets this to
  `production` for TestFlight and App Store builds.
- `com.apple.developer.usernotifications.time-sensitive = true`

The app talks to codeg's push backend (`docs/ios-push.md` in the codeg repo,
branch `fork/solution-plan`). `App/PushRegistration.swift` does the work:

- **Permission.** Asked right after a server is added, on launch when servers
  already exist and the question was never asked (an install that predates
  push), or from Settings › Notifications. Never on a first launch with no
  server. It asks for alerts, sounds and badges. Time-sensitive delivery needs
  no option of its own: it comes from the entitlement, and iOS shows its own
  "Time Sensitive Notifications" switch for the app.
- **Registration.** `registerForRemoteNotifications()`, then
  `POST /api/register_push_device {token, environment, bundleId, name,
  platform: "ios"}` to every saved server, on every launch and whenever the
  token changes (the old token is unregistered first). Each server's
  `server_id` and this phone's device id are kept in `PushServerIndex`
  (UserDefaults).
- **Environment.** Read from the embedded provisioning profile: a development
  profile (a build run from Xcode) means `sandbox`; TestFlight and App Store
  builds carry none or a distribution one, which means `production`. Without a
  profile (the simulator) the `DEBUG` compile flag decides.
- **Unregistering.** Removing a server calls `unregister_push_device {token}`
  on it. Turning push off in the app, or denying notifications in iOS
  Settings, unregisters from every server: a server that believes the phone
  took a critical alert skips its chat-channel fallback.
- **Categories and actions.** `CODEG_CRITICAL` (Acknowledge, Snooze 15 min,
  Open), `CODEG_PERMISSION` (Approve, Open), `CODEG_SESSION` (Open) and
  `CODEG_QUESTION` (Open; the notification service extension swaps in answer
  buttons, see "Waiting for you" below).
  Acknowledge, Snooze and Approve run in the background
  (`ack_critical_session`, `snooze_critical_session`,
  `acp_respond_permission` with `approve_option_id`); Approve needs the device
  unlocked. The server is picked by the payload's `server_id`. An approval that
  fails (answered elsewhere, connection gone) posts an "Already handled" local
  notification that opens the session.
- **Opening.** A tap or Open switches to the push's server and opens
  `conversation_id` with a fresh stack, at the latest message. Opening a
  critical session also acknowledges it, as the desktop does.
- **Foreground.** Pushes show as banners, except one about the session that is
  on screen. Notification Center groups them by `thread-id` (one group per
  session).
- **Presence.** While a session is on screen and the app is active,
  `Networking/SessionPresence.swift` keeps an event socket open with the extra
  `codeg-client.ios` subprotocol and sends
  `{"action":"presence","visible":true,"focused":true,"idle_secs":0,
  "conversation_ids":[id]}` on connect, on change and every 25 s, then
  `visible: false` when the session closes or the app leaves the foreground.
  The server never counts a phone as someone at the desk, but nothing is
  pushed about the session the phone shows. Every other event socket also
  declares `codeg-client.ios` and reports nothing, so it never counts as
  looking.
- **Settings › Notifications** shows the iOS permission, the app-level switch
  and, per saved server, this phone's device preferences on that server (turn
  finished and needs you: always / only when away / off; critical alerts;
  errors) through `list_push_devices` / `update_push_device_prefs`, plus "Send
  test push" (`send_test_push`).

### Waiting for you, reminders and answers from a notification (1.3.27)

codeg keeps one list of everything waiting on the user across a server's
sessions: permission requests, questions, plans waiting for approval, and the
same from delegated sub-agents (filed under their parent). It reminds at 5
min, 30 min, 2 h and then every 4 h until the item is answered (codeg
`docs/ios-push.md` §9).

- **"Waiting for you".** `Features/Sessions/PendingItemsStore.swift` loads
  `list_pending_items` (`{items, count}`, oldest first) for the selected
  server and follows the `app://pending-items` event, which carries the whole
  list on every change. Every event socket of the app hands that event over
  (`EventStream.setGlobalEventHandler`; the rest of the legacy firehose is
  still dropped), so while a session is on screen its sockets carry it; on
  the lists the store keeps one socket of its own, reconnecting with a
  back-off, and it reloads when a socket becomes ready and when a push says
  the list moved. A server without the endpoint shows nothing.
  `WaitingForYouCard` sits above every card of the Chats list (not while
  filtering on iPad): per item the session title (else the folder), how long
  it has waited, the kind (Question, Permission, Plan; Sub-agent for a
  delegated one), the agent and what is asked. A tap opens
  `root_conversation_id` (a sub-agent's parent) at the latest message, where
  the waiting card sits above the message bar. One single-choice question
  with up to six short options shows them as buttons and is answered right
  there (`acp_answer_question` with `questionId` = the item's `request_id`
  and the label); the row hides at once and comes back with the reason if the
  answer fails while the item still waits.
- **Badge.** Every push carries `aps.badge` (its server's count) and a
  silent `kind: "badge"` push follows a change of the count; iOS applies both
  while the app is away (the app asks for badge permission with alerts and
  sounds). In the foreground the app sets the badge itself
  (`setBadgeCount`, `AppBadge`): the sum of the saved servers' counts, from
  the lists it loads, the events and the pushes it sees, so a foreground push
  never applies its own number. Coming to the front it asks every saved
  server for its count and replaces whatever a push left; with notifications
  off in the app the badge is cleared.
- **Answering from the notification.** `NotificationService/` is a
  Notification Service Extension (bundle id
  `io.ashurov.codeg.NotificationService`, Foundation and UserNotifications
  only, sharing `CodegiOS/Shared/QuestionPush.swift` with the app). For a
  `CODEG_QUESTION` push (sent with `mutable-content: 1`) whose `question` is
  `answerable`, single choice, one question and at most four options, it
  registers `CODEG_QUESTION.<FNV-1a of the labels>` with one action per label
  (`ANSWER_<i>`, background, needs the device unlocked) and Open when there
  is room, adds it to the registered set (keeping at most 24 such
  categories), reads the set back so the category is in place, and points the
  notification at it. Multiple choice, several questions, free text or more
  options keep `CODEG_QUESTION` (Open). The app's launch keeps the
  extension's categories when it registers its own. Tapping a label runs the
  app's notification response handler in the background, which sends
  `acp_answer_question` with `connection_id`, `question.question_id` and
  `{answers: [{questionId: question.item_id, labels: [the label]}],
  declined: false}` to the push's server, with the token the app already
  has. An answer that fails (answered on the desktop, the turn ended) posts
  "Already handled", whose tap opens the session.
- **Reminders** read "Still waiting · 2nd reminder" as the subtitle of a
  question reminder (the extension adds it from `reminder` / `attempt`); the
  server's body already says how long the agent has waited.
- **Payload.** `PushPayload` reads `pending_id`, `pending_kind`,
  `pending_since`, `reminder`, `attempt`, `connection_id`,
  `asking_conversation_id`, `approval_id`, `question` and `aps.badge`; a push
  from an older server simply has none of them.
- **Settings › Notifications** shows the server's reminders under its device
  preferences (`get_pending_reminder_settings` /
  `update_pending_reminder_settings`): on or off, Remind after (5 min, 30 min,
  2 h and three other sets), Then every (never, 1 h to 24 h) and quiet hours
  with their times. A save waits 0.6 s (a time wheel sends one request) and
  sends this iPhone's time zone with the quiet hours.
- **Session recency.** Lists order by the later of a session's last activity
  (`updated_at`) and the last time the user opened it on any client
  (`last_viewed_at`, absent from an older server), as the desktop's Recent
  section does: Activity's Running, Recent and Earlier, the Chats folder
  cards and full lists, a folder's sessions and Search. Opening a session in
  the app (its screen on top with the app in front) sends
  `mark_conversations_viewed {views: [{conversationId, ageMs}]}`, batched for
  1.5 s per server, each view with its age so the phone's clock does not
  matter; a server without the endpoint is not asked again until the app
  restarts.

## Session features from the codeg fork

These need Jonathan's codeg server (`fork/solution-plan`). Against an upstream
server they degrade quietly: the new fields are absent and the old behaviour
remains.

- **What a session is doing.** `Models/SessionActivity.swift` ports
  `deriveSessionActivity` (`src/lib/session-activity.ts`) and the held-turn
  rules of `src/lib/background-idle.ts`: Working, Needs you, Idle, Interrupted,
  "Idle — N background tasks running", "Paused — limit resets at … (in …)",
  "Paused by usage limits — continues at …" and "Stopped by usage limits"
  (1.3.22), Connecting… (with the `attach_progress` phase) and Couldn't
  connect. Inputs: the summary's `turn_state`, `limit_pause` and
  `limit_reason`, the attention snapshot
  (`list_conversation_attention`, refreshed with the session list), and, on
  the open session, its own live connection (`awaiting_background`,
  `background_outstanding`). Session rows and the session title show it.
- **Background work in the lists (1.3.10).** The summary's `background`
  (`Models/ConversationBackground.swift`): `task_count`, `tasks` (`id`,
  `kind`, `label`), `out_of_turn`, `held_open`, from the server's live
  connection as of the list read; absent when there is nothing and from an
  older server. `SessionActivity.derive` reads it as codeg's
  `deriveSessionActivity` does: `out_of_turn` is Working, `held_open` (unless
  this client's own connection is idle) and tasks after the turn ended are
  `background(count:)`, attention and an interrupted turn keep their place.
  `ConversationSummary.isRunningForLists` (an open turn, or anything in the
  background) decides Activity's "Running" section, the Activity badge and the
  Folders running counts. The session screen's header leaves it out: its
  summary is refreshed by detail reads, which don't carry it.
- **Insert into the current turn.** While a turn runs, the send button offers
  "Insert into current turn" when the attach snapshot says
  `native_steering_available`. It calls `submit_session_feedback
  {connectionId, text, blocks?}`; a "no active turn" rejection sends the
  message as a normal prompt. Once the agent has it, the message is in the
  conversation, inside the reply (see "Messages sent into a running turn"
  below). Without steering, or with "Send when this turn ends", the message
  waits in a queue above the composer (send now, edit, remove) and goes out
  when the turn finishes, as a prompt of its own.
- **Background work.** While the turn is held only for background tasks
  (`awaiting_background`) and steering is available, send delivers at once, and
  the queue drains into the held turn one message at a time.
- **Continue.** After an agent reply, with an empty composer, a Continue chip
  sends `continue` (the fork's `CONTINUE_PROMPT`). User turns that are exactly
  `continue`, the resume-after-restart prompt, or the continue-after-limit-reset
  prompt render as slim "▶ Continued", "Resumed after restart" and "Continued
  after limit reset" dividers.
- **Model, effort and mode.** Session Details lists the summary's
  `selector_state`. Its config ids (`reasoning_effort`, …) are read from the
  raw JSON, because the shared decoder's snake_case conversion also rewrites
  dictionary keys.
- **New events** decode instead of being dropped: `attach_progress`,
  `awaiting_background`, `background_activity`, `feedback_submitted`,
  `feedback_consumed`.

### The event socket and sending (1.3.4)

`Networking/EventStream.swift`, `Features/SessionDetail/StreamRecovery.swift`
and the send path of `SessionDetailViewModel`.

- **Frame size.** Every socket is made by `EventStream.makeTask`, which sets
  `maximumMessageSize` to 64 MiB. `URLSessionWebSocketTask` defaults to 1 MiB
  and fails the receive with EMSGSIZE ("Message too long") above it, which
  closes the socket. codeg sends bigger frames: `background_activity` re-sends
  a whole growing out-of-turn turn on every update (1.3 to 1.5 MB were seen),
  and an attach snapshot carries a long turn's whole live message.
- **The server knows the limit (1.3.5).** The socket offers
  `codeg-max-frame.67108864` next to `codeg-client.ios`. A codeg server holds
  an iOS socket that offers no such protocol (1.3.4 and older) to the 1 MiB
  default and shrinks bigger frames for it: images move out to
  `/api/live_image/<key>` (the frame keeps a placeholder PNG in `data` and
  the path in `data_ref`), finished tool payloads of a snapshot are left
  out, then long text is cut; such a frame carries `frame_cut: true`.
  `EventStream.frames(from:)` turns that flag into a `.frameCut` frame after
  the frame itself; the session then stops letting the live turn stand in
  for the persisted reply and reloads the transcript (never to fewer turns).
  `InlineImageView` loads a `data_ref` with the session's token.

### What the transcript never hides (1.3.5)

`Timeline/TimelineNode.swift`, `TranscriptView.swift`, `Rendering/ToolCallVM.swift`.

- **Tool pictures.** `images` on a tool result (transcript), on `tool_call` /
  `tool_call_update` and on a snapshot's active tool calls render right after
  the tool's card, live and persisted. A malformed image is skipped
  (`ImageData.lenientList`), never failing the conversation.
- **Reattach.** The live turn rebuilt from a snapshot hides the persisted copy
  of the running reply (the assistant turns after the last user turn) only
  while it holds every tool call id and picture of that copy
  (`TranscriptTimeline.liveCovers`). A trimmed snapshot, or a running prompt
  not yet persisted (so the "running reply" is the previous one), leaves the
  persisted turns visible: a duplicate is recoverable, a hidden reply is not.
- **The window** counts its 50 turns back from the running reply's prompt
  while that reply is hidden, and "Show earlier messages" at the top loads
  older turns where the screen is too short to scroll toward them.
- **A dropped socket never fails a send.** A send opens its stream and waits
  for the server's snapshot before it prompts. A socket that closes before
  then (or a `lagged` / `server_shutdown` detach) is opened again, after
  0.5 s and 1 s; after the third, or a 12 s timeout, the prompt goes without
  a stream and the stream is reconnected once the turn runs. The reconnect's
  snapshot carries the whole reply so far. Only `connection_gone` (retry on a
  fresh connection) and the prompt's own failure can fail a send.
- **Unclear prompts are confirmed.** The prompt carries a client message id,
  which the server echoes as the `user_message` event's id and as the
  snapshot's `pending_user_message.message_id`. When `acp_prompt` fails
  without a clear answer (a transport error, a 5xx) or says a turn is running,
  the app counts the prompt as sent if the stream echoed the id or
  `acp_get_session_snapshot` runs it. A turn that isn't this send's queues the
  message and attaches to that turn.
- **Unclear inserts are confirmed.** `submit_session_feedback` takes no client
  id and answers once the agent took the message, so it gets a 90 s timeout.
  After a transport error the message counts as delivered if the stream's
  `feedback_submitted` matched it, or the snapshot's `feedback` lists a note
  with its text that no other message on screen claims (asked up to three
  times). Otherwise it goes back to the composer, as before.
- **What counts as a running turn.** Only a snapshot whose status is
  `prompting`, or that has a permission, question or plan card, is a turn.
  The server collects output the agent produces after its turn ended (when a
  background task's notification wakes it) into `live_message` while the
  connection is idle. Reading that as a turn showed "Working" on the screen
  while the list, the server and the web client said idle.
- **A turn that ended while the socket was down.** When a reconnect's
  snapshot shows no turn running, the screen asks
  `acp_get_session_snapshot` again a second later and then settles the turn
  like `turn_complete` would (reconcile with the transcript, send the next
  queued message), or reconciles-or-fails when the agent's connection is down.
- **Opening a session whose turn runs.** A socket that drops before the first
  snapshot is retried three times (0.5, 1, 2 s), so the screen doesn't stay
  unattached.

`turn_state` alone stays `running` while a turn is held open for background
work and is null while the agent works out of turn; since 1.3.10 the list
reads the server's live `background` status for both (see "Background work
in the lists" above). Against an older server the list still has only
`turn_state`.

### Mode and options during a turn (1.3.7)

`Features/SessionDetail/AgentOptionsModel.swift` (`AgentOptionsGate` and the
live updates), `AgentOptionsButton.swift`, the event mapping of
`SessionDetailViewModel` and `Interactive/PermissionRequestCard.swift`.

- **What can change mid-turn.** The codeg web composer disables none of its
  selectors while a turn runs (`session-config-selector.tsx`,
  `message-input.tsx`), and the server applies `acp_set_mode` and
  `acp_set_config_option` inside the running turn (the in-turn command loop
  of `acp/connection.rs`). The options sheet now does the same: the mode
  (Claude's `mode` config option, or the mode list of an agent without config
  options) and every config option (model, effort, fast mode, …) stay live
  while the agent responds, also while a permission or plan card waits. A row
  only waits for its own change in flight. The Workspace card keeps the
  folder read-only and the branch locked while busy, with a note saying why;
  the blanket "Options can't be changed while the agent is responding" is
  gone.
- **One difference from the desktop.** The desktop's legacy mode list (agents
  that publish modes but no config options) keeps a mid-turn pick locally and
  sends it with the next prompt. The phone sends it at once with
  `acp_set_mode`, which the server handles mid-turn. Claude's mode is a config
  option on both, sent at once.
- **Applying.** A pick shows at once and is remembered for new sessions, as
  before. The HTTP call only queues the change, so the sheet still polls
  `acp_get_session_snapshot` until the session reports it. A refused request,
  a `set_mode_failed` / `set_config_option_failed` error from the turn, a
  `config_option_rejected`, or a session that stays on the old value put the
  pick back, with "Couldn't change Mode to Bypass permissions: <reason>. It
  stays on Plan." under the selectors, or as the session's notice if the
  sheet was closed. While a change is on its way, an older live value for the
  same option is ignored, so it can't flicker back. The mode list's
  selection key can't collide with Claude's config option id `mode` (they
  shared one before).
- **Live sync.** `mode_changed`, `session_modes`, `session_config_options`
  and `config_option_rejected` are decoded, and the attach snapshot's
  `modes`, `current_mode` and `config_options` seed the sheet. So the phone
  follows a mode the agent leaves on its own (plan mode after an approved
  plan sends `mode_changed` and the new option list) and a change made on the
  desktop. A change made on the phone reaches the desktop the same way: the
  server broadcasts the events to every client of the connection.
- **Errors that are not turn failures.** The web client routes
  `set_mode_failed`, `set_config_option_failed`,
  `grok_model_switch_incompatible_agent`, `goal_control_failed` and
  `image_dropped` to a toast (`routeAcpError`, kind `action`). The phone used
  to end the live reply on any `error` event, so a failed change on the
  desktop ended the reply on the phone. These codes are now a notice and the
  turn goes on.
- **A permission card waiting during a switch.** Neither the server, the
  agent adapter nor the desktop answers a pending request when the mode
  changes; the request was made under the old mode and still needs a tap.
  The desktop card offers only the agent's own options (Claude's "Always
  Allow" can carry a permission-mode change of its own), with no "switch to
  bypass" action, so the phone adds none either. Once the mode changed while
  the card waited, the card says "The mode is now Bypass permissions. This
  request came before the switch and still needs your answer." Later tool
  calls follow the new mode.
- **Checked live** against a codeg server (Claude, a throwaway folder): with
  a Bash permission card waiting, `acp_set_config_option mode=bypassPermissions`
  and `acp_set_mode acceptEdits` each returned at once, `session_config_options`
  and `mode_changed` reached both an iOS-style and a desktop-style socket
  within 100 ms, the card stayed pending, and after it was answered the turn
  ran its next command without asking and completed.

### Right-to-left messages (1.3.9)

`Features/SessionDetail/Rendering/TextDirection.swift`, `MarkdownContent.swift`,
`MarkdownText.swift` and the question, permission and plan cards.

- **The rule** is codeg web's `src/lib/text-direction.ts`, ported as
  `TextDirection.detect`. Code (fenced and inline), `file:` and `codeg:`
  links, other links' targets (not their labels), URLs, e-mail addresses,
  `@handles`, `$skills` and tokens with a `/` or `\` (unless they hold a
  Hebrew or Arabic letter, `ו/או`) are dropped; then quoted spans, unless
  nothing else is left. A quote opens after a space, a bracket or a dash and
  closes before a space or punctuation, so gershayim, geresh and English
  apostrophes stay. Then words are counted: a word is a letter followed by
  letters, combining marks, joiners and apostrophes between letters, and it
  is right to left when its first letter is in U+0590–U+08FF,
  U+FB1D–U+FDFF, U+FE70–U+FEFF, U+10800–U+10FFF or U+1E800–U+1EFFF. No
  words: no direction (the block inherits). Only one kind: that one. A first
  word right to left, or at least 40% of the words: right to left.
- **Blocks.** `MarkdownContent.parseBlocks` decides each block's direction
  from its Markdown source and caches it with the block: paragraphs,
  headings, quotes, a list (from all its items) and each item, a table (from
  all its cells) and each cell. A block is laid out with
  `.environment(\.layoutDirection, …)` (`blockDirection`), so `.leading`
  alignment, a list row's marker and the quote bar go to the right, and
  SwiftUI resolves the text's bidi runs against a right-to-left base
  direction. A list row follows its item's direction, or the list's when the
  item has no letters. `CodeBlockView` is always left to right.
- **Your messages** are plain text with inline Markdown, so
  `TextDirection.lineRuns` splits them into runs of lines that share a
  direction; a line without letters stays with the run before it, and blank
  lines between two runs go with the second. An English message is one run
  and renders as before. Streaming reasoning (verbatim text) takes one
  direction for the whole text.
- **Cards.** The question and each option's label and description of a
  question card, the Other answer field, plan checklist entries, task and
  to-do entries, and a permission card's allowed-action prompts and web
  query or prompt get their own direction. Icons, chips and buttons stay
  where they are.
- **Cost.** A pattern runs only when the text holds a character it needs,
  and the e-mail and path patterns start only at a token's start, so a long
  streaming reply is re-checked in a few milliseconds per update.

### Forking a session (1.3.11)

`Models/SessionFork.swift` (wire shapes and `SessionForkRules`),
`Networking/CodegClient+Fork.swift`, `Features/SessionFork/` (`ForkCapabilities`,
`SessionForker`, `SessionActions`) and the reply footer in
`Timeline/TimelineNodeBody.swift`.

- **What codeg web offers.** "Fork from here" on the footer of every finished
  reply, its only fork entry point: the sidebar, the conversation header and
  the tab menus have no fork, and there is no Duplicate. It needs the tab's
  live connection, a saved conversation and the agent's `fork_supported` (its
  `session/fork` capability). Between turns it forks in place (`acp_fork`, a
  plain branch): the conversation's row and connection move to the fork,
  titled `[Fork] …`, and a new sibling row keeps the original history under
  the original title, at Review. While a turn runs only Claude Code
  (`forks_while_running`) forks, a finished reply, in an agent process of its
  own into a new row (`acp_fork_to_new_conversation`) that opens in a new tab;
  the running turn carries on. Other agents' buttons grey out with "This
  agent can only fork between turns", and the reply being written says "This
  reply is still running…". An in-place fork that meets a turn started under
  it (409 `turn_in_progress`) goes the new-conversation way. Failures read
  "Can't fork yet: this agent can only fork between turns" or "Failed to fork
  session: <the server's message>".
- **On the phone.** Fork in each reply's footer, beside Copy and Read, and
  "Fork from Here" in a long press on the footer; "Fork Session" in the
  session's ⋯ menu and in the long press on every session row (Activity, the
  Chats cards, a folder's list, Search). Fork Session is the web's "Fork from
  here" on the latest reply, so there is no separate Duplicate: between turns
  it forks at the tail (no turn id), a copy of the whole session that
  continues on its own; while a turn runs (Claude Code) it forks the latest
  finished reply, the last assistant turn before the running prompt
  (`in_flight_user_turn_id`, else the last user turn, which is what the
  server's `settle_mid_run_fork_point` accepts). A reply's fork point is its
  last turn: codeg saves one reply as several turns.
- **A live connection.** The app keeps none for an idle session. The forker
  finds the session's connection (`acp_find_connection_for_conversation`) or
  resumes it (`acp_connect` with its `external_id`; the session screen uses
  its own, as the options sheet does), polls `acp_get_session_snapshot` until
  it is `connected` or `prompting`, takes `fork_supported` and whether a turn
  runs from it, and then forks. `acp_fork` carries `conversationId` and
  `folderId`, so a resumed connection that hasn't prompted yet adopts its
  row. A connection that went away in between is resumed once more.
- **After the fork.** From a list, the fork opens on top of the list, so
  Back returns there. From the session, the original goes under the fork (in
  place: the sibling row that now holds it; a new conversation: the session
  itself), so Back returns to the original. An in-place fork reloads that
  row's model from the end (its history shrank) and drops its cached
  transcript, so no screen shows the original under the fork's id. The lists
  refresh at once. On iPad the fork fills the detail column. "Forking
  session…" shows at the top while it runs; a failure is said in the
  session's notice line or, from a list, in an alert.
- **When it is offered** (`SessionForkRules`). Greyed out with the reason:
  an older server ("Needs a newer codeg server"), an agent that said it can't
  fork (learned from every snapshot and `fork_supported` event), a running
  turn for an agent that forks only between turns, the reply still being
  written, a reply the server has no name for (one built on the phone) unless
  it is the last, and a fork under way ("Forking…"). The footer's Fork dims
  and a tap says why; a menu shows the reason under the item.
- **Older servers.** `ForkCapabilities` asks each server once about both
  endpoints, for a connection that can't exist (an empty id): "connection not
  found" means the endpoint is there, 501 `not_implemented` that it isn't, a
  network failure asks again later. Without `acp_fork` the replies have no
  Fork, as in 1.3.10, and Fork Session is greyed out; without
  `acp_fork_to_new_conversation` only forks between turns are offered.
- **The row's long press.** Open, Fork Session, Pin or Unpin, Copy Title,
  and the Archive item of the folder the Folders tab shows the session
  under (a worktree's repo).
- **Checked live** against the codeg server on Jonathan's box
  (0.32.3-fork.187, Claude, a throwaway folder). Both endpoint checks
  answered "connection not found". With no live connection the session was
  resumed (`connected` after 0.5 s, `fork_supported: true`) and `acp_fork` at
  the first reply took 1.7 s: the row became `[Fork] …`, ending at that reply,
  and a sibling row held the whole original. A tail fork kept every turn.
  During a running turn `acp_fork` answered 409 `turn_in_progress`, and
  `acp_fork_to_new_conversation` at the latest finished reply made a new
  `[Fork] …` row while the turn kept running. A reply after the last saved
  prompt is refused ("this reply is still being written…"): Claude saves the
  running prompt only after a while, so until then the latest reply the
  server accepts is the one before the previous prompt, and that is what
  Fork Session forks.

`CodegiOSTests/SessionForkTests.swift` covers the rules (server, agent,
running turn, the reply being written, an unnamed reply), the bodies of both
fork calls and the endpoint check, where a fork lands and how the refusals
read (in place, a turn that started under it, an agent that forks only
between turns, one that can't fork, an older server), where the fork opens

### Messages sent into a running turn (1.3.12)

`LiveTurn.swift` (`SteeredMessage`, `SteerAnchor`), the insert path of
`SessionDetailViewModel` and `Timeline/TimelineNode.swift` (`liveNodes`).

- **The bug.** A message delivered into the turn (Send while the turn is
  held open for background work, "Insert into current turn", a queued
  message drained into a held turn, Continue into a held turn) sat in a strip
  above the message bar, "Inserted", until the turn ended. The agent's answer
  to it streamed into the live reply above it, so the conversation read as if
  the agent had answered nothing. Only the reload at the end of the turn put
  the message in place, and a turn held open for background work can last a
  long time. The Camera Control's send is the message bar's Send
  (`ComposeBar.sendAfterDictation` calls `sendFromComposer`), so a recording
  made while background work held the turn ended up there.
- **What the server says.** Checked live (codeg on the box, Claude Code and
  Pi, a throwaway folder): `submit_session_feedback` answers with the note it
  recorded, `{id, text, created_at, status, delivered_at, blocks?}`, and the
  same note reaches every client of the connection as `feedback_submitted`,
  sent just before the response. Native steering records it `delivered` from
  the start; the pull channel (`check_user_feedback`) records it `pending`
  until `feedback_consumed`. The snapshot's `feedback` lists the turn's notes
  until the next turn's prompt. The snapshot's `live_message` marks no point
  for them. The agent writes its own copy into the transcript as a user turn,
  where it took the message (Claude Code after the running tool call; at once
  in a held turn), and the reply to it follows.
- **Placement.** Once the echo or the response says `delivered` (an older
  server's empty response counts when native steering is on), the message
  leaves the strip and goes into the live reply as a `.steered` segment at its
  current end: it closes the agent's output so far, and what the agent says
  next starts after it. It renders as the user's message card with "Sent
  during the turn" (a bare `continue` is the Continued divider). The codeg web
  client does the same (`STEERING_MESSAGE`). A message sent from another
  client (the desktop) shows the same way. When the turn ends, the reconcile
  replaces the live reply with the transcript, where the agent's copy of the
  message stands in for it, so it shows once.
- **What stays above the message bar.** A message still on its way
  ("Inserting…"), and on the pull channel one waiting for the agent ("Waiting
  for the agent", then "Read by the agent"): the agent reads those as a tool
  result, never as a message. Queued messages stay in the queue until they
  are sent, as a prompt of their own when the turn ends or delivered into a
  held turn, and then join the conversation.
- **Never twice, never lost.** The echo and the response are matched to the
  message by the note id (by text until the id is known, since the request
  carries no client id), so either one places it and the other changes
  nothing. A message the server confirms after its turn left the screen
  isn't put into the next turn: the transcript is fetched once nothing runs.
  One still on its way when the turn ends stays in the strip until the server
  answers. A reply folded into `turns` before the server's copy arrives keeps
  each message as a user turn between the halves of the reply.
- **Rebuilt from a snapshot.** A reconnect, the app coming back to the
  foreground, or a session shown again rebuilds the live reply from the
  snapshot, which joins the text before and after a message into one block.
  Each message keeps a `SteerAnchor`: the last tool call before it and the
  UTF-8 bytes of text and reasoning after that call. The rebuilt reply puts it
  back there (splitting the text block on a character boundary), and at the
  end when the snapshot lacks that tool call. Only messages the snapshot's
  `feedback` still lists are carried over, so one from an earlier turn never
  joins the next.
- **Where the answer's order can differ.** The message goes where the stream
  was when the agent took it. Claude Code and Pi write their copy after the
  tool call that was running, so a tool call that started in between moves
  ahead of the message when the turn is reconciled.
- **Coming back after a failed reply.** Returning to the app with a reply
  that had failed or was cancelled dropped the live reply but left its
  optimistic prompt, beside the server's copy of the same message. The live
  state is now folded into `turns` as phone-made turns, which the re-fetch
  replaces.
- **Not covered.** A session opened while its turn runs, with no earlier
  copy of the turn on this screen, has no anchors for the messages sent
  before it opened: the transcript copies of those the agent already took
  show as before, and the others when the turn ends. Messages sent after it
  opened are placed as above.

### Media in a session (1.3.13)

`Models/MediaReference.swift` (what a message refers to),
`Networking/CodegClient+Media.swift`, and `Features/Media/` (the library,
the stream resolver, the player model, the cards and the viewers).

- **What codeg web does.** It links only Markdown link destinations
  (`remark-file-uri-links.ts`, `rehype-relative-file-links.ts`,
  `link-classify.ts`): a `file://` link opens its path, a relative one is
  joined to the active folder, an absolute one is used as it is, and a
  Markdown picture shows inline only from inside the session's folder
  (`markdown-local-image.ts`). The reply's "New files" card
  (`extractReplyFileChanges`) lists what Write / Edit / apply_patch calls
  wrote, read from their `file_path`, `path`, `notebook_path` (and the other
  `PATH_KEYS`), a `changes` object and a patch's `*** Add File:` headers.
  An attachment that isn't a picture reaches the transcript as
  `[name](file://…)`. The file panel previews video through a streaming
  capability (`video-preview.tsx`) and pictures through `read_file_base64`;
  nothing previews audio. Every request splits the path as `splitAbsPath`
  does: the file's directory is the `rootPath`, its name the path.
- **What the phone finds** (since 1.3.14; see the next section for why).
  `MediaDetector` takes the same links and Markdown pictures (inside the
  folder only), what Write / Edit / apply_patch wrote, paths written out in
  full in prose or a code span (`/tmp/x.png:12`, `` `~/Movies/my clip.mov` ``),
  and a "Saved to …" / "Wrote …" line another tool printed. It never reads a
  command's own text. Relative paths of links and edits join the session's
  folder, `~/` the server user's home (`get_home_directory`, asked once per
  server); a relative name a command printed joins only the `cd` the same
  command opens with. At most 24 files per message, each once.
- **Formats.** Pictures: png, jpg, jpeg, gif (animated in the viewer), webp,
  heic, heif, bmp, tiff, ico; svg in a WebKit viewer with scripts off.
  Video: mp4, m4v, mov, 3gp; webm, mkv and ogv are tried and say plainly that
  they don't play; avi, wmv, flv and mpg are marked unsupported without a
  request, as the web marks them. Audio: mp3, m4a, aac, wav, flac, aif, aiff,
  caf; ogg, oga and opus are tried. Documents in Quick Look: pdf, doc(x),
  xls(x), ppt(x), key, pages, numbers, rtf, usdz.
- **Where they show.** A reply's files are a `.media` timeline node above
  its footer; a user message's own files show inside its card
  (`TimelineNode.attachedMedia`). Detection runs once per turn
  (`MediaRefCache`). The live reply shows its media when it is persisted, as
  the web's card waits for the reply to complete. A link tapped in a message
  opens the file (`MediaLinks`, through the transcript's `openURL`); other
  links open as before. Pictures already in the transcript (tool results,
  `data_ref`) open in the same full-screen viewer. A folder's Files tab opens
  media files in their card instead of the text preview.
- **Streaming.** A video's card mints a capability
  (`workspace_media_capability {rootPath, path}` →
  `{token, url, filename, size, contentType, expiresInSecs}`) and AVFoundation
  reads `/api/workspace_media/<token>/<name>` under the server's base URL with
  Range requests, for the poster frame and length too: a seek is a new
  request at the new offset, nothing is downloaded first, and AVPlayer keeps
  only its forward buffer (30 s). The token is the only credential, so the
  player sends no Bearer header. `MediaStreamResolver` keeps one capability
  per file and mints another a minute before the server's 15-minute idle
  limit (counted from the mint) or its 8-hour cap. `MediaPlayerModel` mints
  again before resuming a stream that sat unused past the idle limit, and
  when an item fails it reads the first 16 bytes with a Range request
  (`MediaProbe`): a 404 "Media link is invalid or expired" re-mints and
  resumes at the same position (twice at most), a missing file or a Matroska
  header says why.
- **Audio, pictures, documents.** Audio is tried as a stream first: codeg
  fork.190 and later mint capabilities for audio too (`audio/mpeg`,
  `audio/mp4`, …), so it streams like video. An older codeg answers "Only
  video files can be streamed"; the phone then downloads audio
  (`download_workspace_file`, up to 200 MB) and plays it from the iPhone.
  Pictures (up to 40 MB) and documents (up to 100 MB) are downloaded. Downloads are kept in
  `Caches/Media` (`MediaDiskCache`, 256 MB, least recently used out), per
  reply, so a file written again under the same name is fetched again for the
  newer reply; decoded pictures are scaled off the main thread
  (`TranscriptImages`) and held in memory. Videos are never kept.
- **The audio session.** A clip plays through `AudioSessionOwner` with a
  `.media` use (`.playback`, `.moviePlayback`). `MediaPlaybackCenter` lets one
  clip play at a time: starting one pauses the other and stops read aloud;
  read aloud starting, or dictation taking the session
  (`audioSessionUseWillChange`), pauses the clip. A paused clip gives the
  session back after 30 s. The Camera Control's standby microphone steps
  aside while a clip holds the session (`mediaPlaybackWillClaimAudio`), as it
  does for read aloud. The lock-screen controls go through one
  `RemoteCommandRouter` that read aloud and clips claim in turn, so a press
  reaches one of them; clips can also be scrubbed from there.
- **Video player.** `AVPlayerViewController`, presented from the top view
  controller so Picture in Picture can dismiss it and bring it back; AirPlay
  is the system's. Its Now Playing is the model's. Closing it (its X, a
  swipe, or closing Picture in Picture) stops the clip; a clip that fails
  closes it with an alert saying why.
- **Older servers.** Without `workspace_media_capability` (501) a video's
  card says "This needs a newer codeg server"; audio and pictures still come
  through `download_workspace_file`. Without that too, every card says so.
- **Checked live** against the codeg server on the box (port 3080, a
  throwaway folder in `/tmp` with an mp4, an m4a, an mp3 and a png made with
  ffmpeg): the mp4 capability answered 200 with `video/mp4`, its size and
  `expiresInSecs` 900; the byte endpoint answered 200 with
  `Accept-Ranges: bytes`, 206 with the right bytes for `bytes=0-15`,
  `bytes=1000-1999`, a 64 KiB middle span and `bytes=-100`, and 416 with
  `bytes */58508` past the end. The m4a, mp3 and png were refused 400
  ("Only video files…") and downloaded byte for byte. A missing file was 404
  "File does not exist", a missing folder 404 "Workspace folder does not
  exist", `..` 400, a revoked or unknown token 404 "Media link is invalid or
  expired", an unknown endpoint 501. AVFoundation on the box read the
  capability URL's length (4.00 s) and poster frame over HTTP, played, and
  seeked to 3 s; a revoked link failed the item (`NSURLErrorDomain -1100`) and
  a fresh mint played on.

  - a Write / Edit / apply_patch target (its `file_path` and codeg web's

  - a Markdown link or picture, as codeg web resolves it;

    "to" / "as" / "at" / "in" between the verb and the name, and no error

  - an attachment (`[name](file://…)`).

  expression) is never read. A relative name a command printed joins only

  `list_directory_with_files` per directory however many files and messages
  name it (codeg had no stat endpoint; since 1.3.22 a server with
  `stat_paths` answers in one request, see "Catching up with the server
  (1.3.22)"). A file that isn't listed doesn't show; a directory that isn't there ("Path is not a directory") means its
  files aren't either. The one exception is a file the reply wrote with
  Write / Edit / apply_patch and that is gone since: it is listed, struck
  through, as "Deleted". An answer is kept for 10 minutes when the file is
  there and 30 s when it isn't, so a file made a moment later shows on the
  next rebuild. A server that can't answer (an older codeg, the network) and
  a hidden name (a listing leaves out dotfiles) leave the card to find out
  on its own, as 1.3.13 did. The transcript rebuilds once per batch of
  answers (`MediaPresence.version` in `TranscriptView`'s memo key).
- **The row.** One picture or video under a message shows inline, at most
  180 pt tall (`MediaCard(compact:)`); one audio file is its player, one
  document its row. Several files fold into one row, as codeg web's "New
  files" card folds a reply's files and as `ToolGroupCard` folds tool
  calls: up to four 26 pt thumbnails (a picture's, a video's poster, a
  symbol for audio and documents), the summary ("3 images · 1 video · 2
  audio files · 1 PDF · 1 deleted") and a chevron. Tapped, it opens into a
  list: a 36 pt thumbnail, the name (truncated in the middle), the type and
  size from the listing; a picture opens full screen, a video plays, a
  document opens in Quick Look, an audio file is its inline player. The
  chevron and the order follow the layout direction, so Hebrew reads right
  to left.
- **Attaching a video.** The Photo Library picker matches images and videos

  type, high quality, five minutes at most); Files takes `.movie` types. A
  video is an `Attachment` with an `AttachmentUpload` job:
  - *fetching*: the picker's `loadTransferable` (a `FileRepresentation` of
    `.movie`), its `Progress` shown while an iCloud video downloads; a
    recording or a file from Files is copied into the app's own temporary
    folder first;
  - *compressing*: an H.264 MP4, MOV or M4V within the limit is sent as it is
    ("Original"); HEVC, another codec or a larger file is exported with
    `AVAssetExportSession` to H.264 MP4 at 720p, or 540p, 480p or medium
    quality (about 360p) when AVFoundation's estimate
    (`estimatedOutputFileLengthInBytes`) or the written size is still over
    the limit; when even that is over, it says the video is too long and to
    trim it in Photos;
  - *uploading*: `upload_attachment`, multipart, with the conversation's

  The chip shows the poster and length when it is done, and a ring with the
  phase until then; a failed one has a red outline and, tapped, says why with
  Try Again (the compressed file is kept for it) and Remove. Send is greyed
  out until every video is uploaded; an attempt to send, insert or queue
  earlier says to wait. The prompt sends a `resource_link`
  (`{uri: file://…, name, mime_type}`), the block codeg web sends for a file
  that isn't a picture; the server shows it as `[name](uri)` and Claude Code

#### What the codeg server should change

Both done in fork.191 and used since 1.3.22 (see "Catching up with the
server (1.3.22)").

- ~~**A larger limit for video attachments.**~~ `upload_attachment` takes at
  most 20 MiB a file (`UPLOAD_MAX_BYTES`, `web/handlers/files.rs`, mirrored in
  `commands/remote_proxy.rs` and `src/lib/api.ts`), the cap meant for
  pictures that `prompt_hydration` reads back into the prompt. A video is
  only linked, never inlined, so it could take a cap of its own: for a part
  whose content type is `video/*` or `audio/*`, a limit of a few hundred MB
  (an env setting such as `CODEG_UPLOAD_MAX_MEDIA_BYTES`), with the route's
  `DefaultBodyLimit` raised to match (the handler already streams to disk)
  and the `CODEG_UPLOAD_MAX_TOTAL_BYTES` reservation sized from the request's
  `Content-Length` rather than the picture cap. Until then the phone
  compresses to fit, which keeps about half a minute at 720p and a couple of
  minutes at 360p. A resumable upload (an upload id and an offset per chunk)
  would let a large one survive a dropped cellular connection.
  `upload_workspace_file` has no limit but writes into the project's folder,
  which is not where a chat attachment belongs.
- ~~**A stat endpoint.**~~ `stat_paths {paths: [...]}` →
  `[{path, exists, isFile, size, modifiedMs}]` (a few hundred paths at most)
  would answer the existence check in one request, without listing whole
  directories (`list_directory_with_files` also opens every subdirectory to
  fill `hasChildren`, and leaves out dotfiles).

### Keeping the reader's place (1.3.16)

`Features/SessionDetail/TranscriptAnchoring.swift` (`ScrollAnchorMath`,
`TranscriptScrollBridge`, `TranscriptCollectionFinder`),
`ReadingPosition.swift` (`ReadingPosition`, `ReadingRestore`,

of `SessionDetailViewModel`.

- **Why it jumped.** Three causes.
  - *Older messages went in above the reader and the list didn't move with
    them.* The transcript is a SwiftUI `List` (a `UICollectionView`), which
    keeps its content offset when rows are inserted above the visible ones,
    so each page of older turns pushed the view down by its own height:
    the message being read left the screen, and the reader, now near the
    top of the new page, set off the next page. `.defaultScrollAnchor(.bottom)`
    only placed the first paint. The swap of the "Show earlier messages" row
    for a spinner (a different height) moved it again.
  - *Every return scrolled to the bottom.* The view's scroll state
    (`stuckToBottom`, the window start) lived in the view, which a new screen
    rebuilds, and it scrolled to the bottom whenever it appeared: a new screen
    (Back and open again), but also the same screen coming back from another
    tab or from a screen pushed over it. The cached open forced a re-pin too.
    The 1.3.6 model store kept the transcript, but not where the reader was
    in it.
  - *Background work forced a re-pin.* A reattach to a running turn (the
    cold attach on open, a reconnect after a drop, the app returning) and the
    refresh after a missed live turn bumped `stickTick`, the forced re-pin
    meant for the user's own send, so a reader scrolled up was pulled down.
  Measured on the CI simulator with the whole app and a 700-turn session
  (rows of many heights) scrolled up two screens at a time, each
  scroll then watched on every display frame for half a second: without the
  anchoring the row at the top of the screen moved by 15,717 to 25,951 pt each
  time older turns went in; with it, by 0.0 pt on every one of 700 frames
  over 30 scrolls and 6 reveals (`TranscriptScrollTests`, written to
  `transcript-scroll.txt` in the `session-list-screenshots` artifact).
- **Holding the row still.** `List` has no API for keeping a row where it is,
  or for scrolling to a row plus a few points. `TranscriptCollectionFinder`
  reaches the list's `UICollectionView` (from a zero-size probe in its first
  and last rows, or beside it), and `TranscriptScrollBridge` maps the list's
  items to the transcript's rows by order (the top row, the nodes, the bottom
  anchor). While the reader is scrolled up it holds the row at the top of the
  screen: it records the row's distance below the content offset whenever the
  reader's scroll moves or settles, and puts the row back at that distance on
  every content size change and every offset change that isn't the reader's
  (KVO, inside UIKit's layout pass, before the frame is drawn). Older turns
  put in front, a picture above that decoded taller than its placeholder, a
  row above that re-rendered, the keyboard: none of them moves what is on
  screen. While following the latest message nothing is held and the bottom
  is followed as before. Only the reader's own scroll moves the hold; an
  animated programmatic scroll (the jump to a reply's question, the status
  bar's scroll to the top) releases it until it settles.
- **What the measurements showed on the way.** A trace of the bridge on the
  CI simulator found two things a first version got wrong. SwiftUI computes
  the rows in `body` a frame or two before it hands them to the collection
  view, so mapping items by the newest rows failed (62 items against 134
  rows) and the row was put back only once the counts matched, 2 to 3 frames
  (about 40 ms) late; the bridge now keeps the last four row lists and reads
  the one as long as the collection view's items. And SwiftUI moves the
  offset as it hands an update over (777.7 to 562.0 pt), before the layout
  has the new rows; while the item count differs from the last laid-out one,
  such an offset change goes back to where the row was held, until the
  layout catches up and the row is put back exactly. A version that let go
  of the hold whenever the offset had moved since it was taken let three of
  five reveals through (14,805, 8,362 and 8,552 pt).
- **Covering the hand-over.** Holding the row puts it back as soon as the
  layout has the new rows, but SwiftUI gives the collection view the new
  items a frame or two before it lays them out, so even with the hold those
  frames showed the content shifted by the inserted height (3,744 pt per
  reveal of 60 turns in the measurements) before it snapped back. Older turns
  therefore go in only while the list is at rest (a reader still scrolling
  gets them when the scroll ends; with 1.5 screens of margin that is before
  the top), under a picture of the screen (`snapshotView`) laid over the
  list, which is taken off once the items are laid out and the held row has
  been in place for two frames (0.6 s at most; a touch takes it off at once).
  What the reader sees is the same screen throughout, then the same screen
  with older turns above it. Measured: 6 reveals
  covered 80 frames in all, about 220 ms each on the simulator (626 ms at most,
  the cap); the row at the top of the screen moved 0.0 pt on every frame
  shown.
- **Bringing older turns in.** Within 1.5 screens of the top
  (`ScrollAnchorMath.isNearTop`, read by the bridge from the collection
  view's own offset: SwiftUI's scroll geometry doesn't see an offset set on
  the collection view, so a reveal driven by it never came after one of the
  bridge's corrections), the next 60 held turns join the window, in
  a transaction without animation. Once fewer than 100 held turns are left
  above the window, the server's next page of 150 is fetched in the
  background; it joins `turns` without changing the window (the window's
  start is a global index), so the reader keeps scrolling through what is
  held while it comes. The proximity is re-read whenever the content grows,
  so a reveal that leaves the reader near the top brings in the next one.
  The top row is one row of a fixed 40 pt, a button or a spinner while a page
  the reader waits for is on its way, so neither pushes the content.
- **Pictures and media keep their height.** An inline picture decoded before
  is drawn at once (the memory cache is read when the view is made); one not
  decoded yet takes its final height from its proportions when they are
  known: decoded before (`TranscriptImages.aspect`, kept after the picture
  is evicted) or read from the file's first bytes without decoding it
  (`ImageDimensions`: PNG `IHDR`, GIF, JPEG `SOFn`, not a JPEG with an Exif
  block that might rotate it). A media card under a message reserves its
  full 180 pt (what a screenshot takes there) or the picture's known
  proportions, and a video card starts from the poster it read before. What
  still changes height after loading is held still by the bridge when it is
  above the reader.
- **Saving the position.** When scrolling settles, when the screen goes (Back,
  another tab) and when the app leaves the foreground, the transcript reports
  the row at the top of the screen (a persisted row, which keeps its id across
  reloads, rather than one of the live reply) and how far into it the top of
  the screen is, or that the reader is at the latest message. The model keeps
  it and saves it in `ReadingPositionStore` (UserDefaults
  `codeg.readingPositions.v1`, 1.5 s after the last change, at once when the
  session isn't looked at), keyed by the server's endpoint and token (the
  transcript cache's key) and the conversation id, at most 400 sessions,
  least recently saved first out, pruned with the transcript cache when a
  server goes. A position also keeps the row's turn, its exact server time
  (turn ids are positions, `turn-41`, so after a rewrite the same id can be
  another message), the window's start and how far the transcript went when
  the reader last saw its end. The window's start now lives in the model too.
- **The restore rule** (`ReadingRestore.decide`). At the latest message when
  the reader was there when they left (it keeps following new replies), when
  nothing was saved, and when the session is opened from a notification or a
  link (`AppModel.openSessionFromOutside`: they are about something new; a
  screen showing that session jumps there). Otherwise where they left it:
  from a list, Back, another tab, the app coming back, a relaunch. A saved
  row that is gone falls back to the first row of its turn, and a turn whose
  server time changed (a rewritten history) or that isn't held opens at the
  latest message. The decision is made once per screen.
- **Restoring.** The window opens wide enough to show the saved row; the list
  starts from its top, hidden, the bridge scrolls to the row and offset in the
  first layout pass that has it, checks it again for a few frames (SwiftUI may
  still place its own first offset), and then shows the list. If the bridge
  can't reach the list, SwiftUI scrolls to the row's top after 0.7 s.
- **New messages.** Turns that arrived after the end the reader last saw, or a
  live reply that grew while they were scrolled up, turn the latest-message
  button into "New messages ↓"; nothing scrolls. A tap goes to the latest
  message, as before. Only the reader's own scroll, their send, that tap and
  an open from a notification move the view to the bottom; reattaches,
  reconnects, refreshes and a missed live turn's reload follow the bottom only
  for a reader already there.

`CodegiOSTests/ReadingPositionTests.swift` covers the store (persistence
across launches, the keying, the cap, pruning), the restore rule and its

### Editing a message (1.3.16)

`Models/MessageEdit.swift` (`ForkMode`, `MessageEditRules`, the targets,
blocks and wording), `Features/SessionDetail/MessageEditor.swift` (the sheet
and its right-to-left text field), the edit part of `SessionDetailViewModel`,
`Networking/CodegClient+Fork.swift` (`mode`, the capability check) and the
user message's long press in `Timeline/TimelineNodeBody.swift`.

- **What codeg web does** (`src/lib/edit-message.ts`,
  `user-message-editor.tsx`, `computeUserEditTargets` and the host's
  `handleEditUserMessage`). A settled user message has Edit message when what
  comes right before it is a reply (not another message, a system note or a
  compaction divider; not the first loaded message while older ones are on
  the server), and the agent's fork lands exactly on a named reply or refuses
  (Claude Code, Codex, DeepSeek; Pi forks at the tail when it misses).
  Saving forks at that reply's last turn with `acp_fork {…, mode}`: strict,
  so a reply the agent can't name refuses (400) instead of forking at the
  tail, which still holds the message being replaced. `edit_in_place`, the
  default, re-points the conversation's own row at the fork and hides the row
  holding the original (born soft-deleted); `edit` (Settings › "Keep the
  original as a separate conversation when editing") leaves it in the
  sidebar as "… (before edit)". The host reads the forked history until the
  row is on the forked session (four tries, 400 ms apart times the try), then
  sends the edited text, with the message's images, as an ordinary prompt.
  The first message has no reply before it: saving opens a new conversation
  on the same agent and folder with the edited text, and this one stays.
  Greyed out with `editBusy` while a turn runs (or a message just sent isn't a
  turn yet), `editQueued` while messages wait in the queue, `editNotReady`
  while the reply before it is still being written; another edit being saved
  counts as busy. A reply the post-turn reparse never named is found by the
  message's place among the user turns in a fresh read, its text matching.
- **On the phone.** A long press on your message: Copy and Edit Message (the
  reason under it while it is greyed out; the message's text no longer takes
  the long press for its own Copy). The editor is a sheet: the text as sent
  in a field that follows its direction like the web's `dir` (a Hebrew or
  Arabic message right-aligned and right to left whatever the app's
  language), the pictures as fixed chips with "Attached images are sent again
  with the edited message", the web's hint for the outcome, the blocked
  reason, Cancel and Save & send (with the web's saving label and a spinner).
  A failed save keeps the sheet and the text, with the web's message. The
  keep-original setting is Settings › General › Editing Messages (off, as on
  the web; kept on the iPhone as the web keeps it per browser). After an edit
  in place or as a branch, the same screen shows the forked history with the
  edited message going out (the cached transcript of the original is dropped
  and the saved reading position forgotten); a first message's new
  conversation opens on top, so Back returns to the original.
- **The phone's own steps.** No connection is kept for an idle session, so
  saving finds the session's connection or resumes it (`acp_connect` with its
  `external_id`), waits for it to be `connected` (a turn found running is
  busy), forks, reads the forked history and sends. A fork whose history
  didn't load is remembered: Save & send again goes on from it instead of
  forking twice, as the web does.
- **Older servers.** The phone asks each server once, with `acp_fork
  {connectionId: "", mode: "codeg-ios-probe"}`: a server that knows the modes
  refuses the unknown one while reading the body (422 "unknown variant")
  and touches nothing; an older one ignores the field and answers "connection
  not found"; one without forking answers `not_implemented`. Without edit
  modes there is no Edit Message at all (an older server would take an edit
  as a plain branch and continue the original).
- **Checked live** against the codeg server on the box (fork.193, port 3080,
  `/tmp/ios-edit-test` with hooks off, a throwaway Claude Code conversation,
  through the endpoints the app calls): the probe answered 422. Two prompts
  (APPLE, BANANA), then `acp_fork … mode: edit_in_place` at the first reply's
  last turn took 1.1 s; the row moved to the forked session with its history
  ending at the first reply, its title kept, the sibling holding the original
  not listed; the edited message (CHERRY) went out on the same connection and
  the transcript read APPLE, CHERRY with no BANANA. `mode: edit` at the same
  reply left the original listed as "… (before edit)" holding APPLE, CHERRY,
  and the row went on with DATE. A first-message edit (`create_conversation`,
  `acp_connect`, `acp_prompt`) made a new conversation with ELDERBERRY and
  left the original unchanged. The rows were deleted (codeg's delete is a
  soft delete; the hidden sibling was born that way), the folder removed from
  the workspace and history, and the folder and its Claude project directory
  deleted.

#### What the codeg server should change

- **Turn ids that survive a rewrite.** Transcript turn ids are positions
  (`turn-41`); a compaction or an in-place fork gives the same id to another
  message, so a saved reading position checks the turn's server time too. An
  id taken from the agent's own message id (Claude's entry uuid, where there
  is one) would let a position, a fork point and an edit target survive a
  reload without that check.
- **A capability list.** The phone learns what a server can do by asking
  endpoints about a connection that can't exist (the fork endpoints, the edit
  modes, the media capability). A `server_capabilities` answer
  (`{"forkModes": ["branch", "edit", "edit_in_place"], …}`) would replace the
  probes.

### Messages that could not be sent (1.3.19)

`Features/SessionDetail/Outbox.swift` (`SendFailure`, `OutboxStore`), the send,
queue and insert paths of `SessionDetailViewModel` (`keepUnsent`,
`scheduleUnsentResend`, `restoreOutbox`) and the queued rows in
`SessionActivityViews.swift`.

- **The rule.** A message the user sent is kept until the server has it. When
  a send fails (no network, a timeout, a 5xx, a server restart, the agent's
  connection gone), the message leaves the conversation and waits at the
  front of the queue above the message bar, marked "Not sent" with the
  reason: "Connection lost — will resend", "No answer — will resend",
  "Server error — will resend", "Interrupted — will resend", "Refused by the
  server". It is never put back into the message bar, where the next message
  may already be half written (1.3.16 put it back only when the bar was
  empty, and lost it otherwise). A failed insert into a running turn is kept
  the same way, for the turn's end. A busy turn and the account pool still
  queue the message unmarked, as before.
- **Sent again by itself.** A failure that only means the server could not
  be reached goes again after a backoff (1 s, 2 s, 4 s … up to 30 s) and when
  the app comes back to the foreground; an unexpected server error gets three
  tries; a message the server refused (413, invalid) waits for Send now and
  holds the queue behind it, keeping the order.
- **Exactly once.** Every attempt of a message carries one client id: the
  `client_message_id` of `acp_prompt`, and the `clientId` of
  `submit_session_feedback` (the note is recorded under it). The codeg server
  (fork, `acp/message_receipts.rs`) keeps a receipt per conversation for every
  id it accepted, written to its database, and answers a repeat with
  `{"duplicate": true}` (or the note it recorded) instead of delivering it
  again — also after a restart, and also when an insert that went through is
  resent as the next prompt. The 1.3.4 check against the echo and the snapshot
  still runs first; a duplicate answer drops the attempt's placeholder and
  re-reads the session. An older server ignores the id, so there a resend
  after a lost answer can still arrive twice.
- **On disk.** The queue and the messages on their way are stored per server
  (its address) and conversation in Application Support/Outbox, on every
  change. A message is recorded as on its way before its send starts, so a
  screen that closes, an app that is killed or suspended mid-send gives it
  back: when the conversation opens again it is at the front of the queue,
  marked interrupted, and goes again under its id. Pictures are stored with
  the message; an uploaded video comes back as its reference in the text.
  Stop on a running turn drops what was on its way, as the user asked.
- **After a restart.** A prompt for a connection the server no longer has is
  answered with a 500 that says "connection not found"; that now counts as a
  stale connection, so the send opens a fresh one and tries once more before
  it is kept as not sent.
- **Not covered.** A brand-new task whose conversation could not even be
  created keeps its message in the queue while the screen is open, but there
  is no conversation to store it under.
### Fork progress and provider errors (1.3.21)

`SessionActions.inFlight` (`ForkInFlight`), `SessionForkRules.whileForking`,
the banner in `App/RootView.swift`; `Models/ProviderError.swift` and
`Rendering/ProviderErrorNotice.swift`.

- **A fork in flight.** One fork runs at a time. `start` records the session,
  the point (a reply or the latest) and the session's title, and refuses any
  other fork until the first opens or fails, so repeated taps on a reply, the
  ⋯ menu or a row start nothing. The banner at the top reads "Forking
  “<title>”…" ("Forking session…" without a title) with a spinner from the
  tap until the fork opens, and VoiceOver announces it. The reply it was
  taken from shows "Forking…" with a spinner; every other Fork and Fork
  Session is greyed out with "Another fork is in progress".
- **A provider's refusal or error.** Mirrors codeg web's
  `src/lib/provider-errors.ts`. Claude Code reports a failed API request as
  `API Error: <status> <the provider's message>` (or the JSON error body).
  When that is a sub-agent's (Agent/Task) result, the card turns red and
  shows "Sub-agent stopped: <reason>" (usage-policy block, rate limit,
  overloaded, rejected request, other error), the provider's link, and the
  raw text under Details; a turn error in that form shows "Stopped:
  <reason>" the same way. Recognition is narrow: the text must be the error
  itself (the prefix, after at most an "Error:" lead-in; a policy notice's
  own opening; or a provider JSON error envelope) and short, so a result

  codeg web does for a folded reply. Presentation only.

### Catching up with the server (1.3.22)

What the codeg fork (`fork/solution-plan`) gained since 1.3.21 that the app
now follows: a new continuation prompt, dictation kept as spoken, forking
while a Pi reply runs, the resumable upload, and the account pool's waiting
and exhausted states.

#### The continuation's new wording

`ContinuePrompt.limitContinue` and `earlierLimitContinues`
(`Models/SessionActivity.swift`). codeg's `LIMIT_CONTINUE_PROMPT`
(`src-tauri/src/acp/limit_continue.rs`) now reads "Your usage limit has
reset. First resume any sub-agents the limit stopped, each from where it
stopped with its context intact rather than starting it over; then continue
the task you were working on when the usage limit was reached. Do not repeat
work that is already complete." Both it and the earlier wording ("…Continue
the task you were working on when the usage limit was reached; do not repeat
work that is already complete.") are the "Continued after limit reset"
divider, matched exactly on the trimmed text, as codeg web's
`isLimitContinuePrompt` does, so neither shows as a message the user typed.

#### "Kept as spoken"

`DictationRefineResult.keptOriginal`, `DictationRefineFallback.rejected`
(`Features/Dictation/DictationRefine.swift`). `refine_dictation` answers
`keptOriginal: true` when it rejected the model's answer (a refusal, a reply
to or comment on the dictation, nothing, a cut-off answer, most of it
dropped) and its one stricter retry gave nothing usable either; `text` is
then the dictation as it came. The app inserts its own words unchanged and
the composer's dismissible notice says "Kept as spoken" (in the string
catalog; zh-Hans "已按原话保留"). An older server never sends the field, and
nothing changes there.

#### Forking while a Pi reply runs

`SessionForkRules.forksWhileRunning(_:adapter:)`,
`ForkCapabilities.agentForksWhileRunning`. pi-acp 0.0.34-steering.3 writes a
fork from the session file, skipping a half-written last line, and says so at
`initialize` (`_meta.forkPoint.whileRunning`); codeg passes that on as the
session snapshot's `fork_while_running` and the `fork_supported` event's
`while_running`. The app records it per server and agent beside
`fork_supported` (only when the agent forks at all: the server reports
`false` until the adapter has started), and offers a fork while a turn runs
when the server says the adapter can, with Claude Code always able, as
codeg's `fork_adapter_of` and codeg web's `supportsForkWhileRunning` have it.
Without the server's word (an older server, or no live session of that agent
seen yet) Claude Code and Pi are offered it; an older pi-acp is then refused
by the server ("this agent can only fork between turns"), which the app
already reports.

#### Large videos, audio, resumable uploads, stat_paths

`Networking/CodegClient+Uploads.swift` (`upload_limits`, the resumable
calls, `stat_paths`), `Networking/ResumableUpload.swift`
(`ResumableTransfer`), `Features/SessionDetail/VideoAttachment.swift` (the
job, `VideoPolicy`, `AttachmentUploadLifecycle`, `AudioAttachmentPrep`),
`Features/Media/MediaPresence.swift`.

- **What the server takes.** codeg fork.191 answers `POST /api/upload_limits`
  with `{maxFileBytes, maxMediaBytes, mediaTypes, maxTotalBytes,
  remainingTotalBytes, resumable: {chunkBytesHint, idleTimeoutSecs,
  maxActive}}`: 20 MiB for pictures and other files, 1 GiB for `video/*` and
  `audio/*` (`CODEG_UPLOAD_MAX_MEDIA_BYTES`), pieces of 8 MiB suggested,
  an idle upload dropped after 24 h. The app asks once per server
  (`UploadLimitsCache`: an answer is kept for an hour; "unknown call" for ten
  minutes, so an upgraded server is noticed). A 404, 405 or 501, or an
  answer that doesn't parse, is a server before fork.191
  (`ServerUploadLimits.legacy`: 20 MiB for everything, no resumable
  upload), and the job then does exactly what 1.3.14 did; the one
  `upload_limits` request is the only difference.
- **Which video goes.** Against a server that reports its limits:
  - *Original* (the default) sends the file as the iPhone has it, in any
    codec (HEVC included) and any container, whenever it is within
    `maxMediaBytes`. Only a larger one is exported, to H.264 MP4 at 1080p,
    or 720p, 540p, 480p or about 360p when that is still over.
  - HEVC is not converted to H.264, because nothing on the way needs it:
    codeg stores the file and serves byte ranges, it never decodes it; the
    iPhone, Safari, the codeg desktop app's WebKit view and Chrome on a Mac
    play HEVC; an agent that looks at a video extracts frames with ffmpeg,
    which reads HEVC. A transcode on the phone would cost about the clip's
    length in time and battery and lose quality on every upload. The one
    place HEVC fails is a browser without it (Firefox, Chrome on Linux)
    showing the clip in codeg web, and *Compressed* covers that.
  - *Compressed* exports to H.264 MP4 at 720p (down the same ladder to fit);
    an H.264 MP4, MOV or M4V whose shorter side is 720 or less goes as it
    is. The choice is in the long-press menu of the video's chip ("Send the
    video": Original / Compressed (720p)), offered for a video on such a
    server until it is uploaded. Switching starts over from the picked file
    and cancels the other upload on the server. The choice is stored
    (`attachments.videoQuality` in the user defaults) and used for the next
    video.
  - A file AVFoundation can't read (WebM, Matroska, …) goes as it is within
    the limit, without a poster.
  - On an older server the 1.3.14 rules stay: an H.264 MP4, MOV or M4V
    within 20 MiB as it is, anything else exported at 720p, 540p, 480p or
    360p to fit.
  - Exports go to an `export-<id>/` folder beside the picked file. 1.3.14
    wrote the export of an H.264 `clip.mp4` over 20 MiB onto `clip.mp4`
    itself, which deleted its own source and failed.
- **The resumable upload.** `ResumableTransfer` sends the prepared file:
  `upload_attachment_create {fileName, size, mimeType, sessionId}` (the
  conversation's bucket, as `upload_attachment`'s `session_id`), then
  `PUT /api/upload_attachment_chunk?uploadId=…&offset=N` with
  `chunkBytesHint` bytes of the file as the raw body
  (`application/octet-stream`, read with a `FileHandle` off the main
  thread), each answer's `offset` being where the next piece starts, then
  `upload_attachment_complete`, whose `{path, name, size, mimeType}` is what
  `upload_attachment` answers, so the prompt's `resource_link` and the card
  are as in 1.3.14. The chip's ring is the server's offset plus what the
  current piece has sent (`didSendBodyData`); VoiceOver reads "Uploading,
  40 percent, 61 MB of 152 MB".
  - A piece at the wrong offset (409 `errors.upload.offsetMismatch`) starts
    again at `i18n_params.offset`. A piece taken over by a newer request
    (409 `superseded`) and an early complete (409 `incomplete`) ask
    `upload_attachment_status` and go on from its offset.
  - An upload the server no longer has (404 `errors.upload.notFound`: a
    restarted server keeps none, an idle one lapses after a day) starts
    over from zero with a new create, three times at most.
  - A network failure or a 5xx waits 1, 2, 4, 8, 15, then 30 s, asks
    `upload_attachment_status` and goes on; the bytes of a piece cut off
    midway stay on the server, so little is sent twice. Eight failures in a
    row with nothing getting through mark the chip failed; the upload id is
    kept, so Try Again goes on where the server stopped.
  - Too large, the upload space full and too many uploads in progress fail
    at once, in the server's terms. A proxy that refuses `PUT` (405) gets the
    piece as a `POST`, which codeg takes too.
  - Pieces go through their own session: a minute without a byte ends a
    piece (the server keeps what arrived), and a request waits up to half an
    hour for the network to come back (`waitsForConnectivity`), the chip
    showing a Wi-Fi symbol meanwhile (`taskIsWaitingForConnectivity`).
  - Removing the chip cancels the request, tells the server
    (`upload_attachment_cancel`, which deletes its staging file and frees
    its quota) and deletes the copies on the iPhone.
- **In the background.** `AttachmentUploadLifecycle` holds a
  `beginBackgroundTask` while any upload runs, so an upload keeps going
  for the time iOS gives an app that leaves the screen (about 30 s). Just
  before that time runs out every upload pauses: its request is cancelled
  (the server keeps what arrived) and the chip shows a pause symbol. On
  `willEnterForeground` each one asks `upload_attachment_status` and goes
  on. An app suspended without that warning finds its request failed when
  it wakes, which is a network failure like any other: status, then go on.
  An export or an iCloud download stopped this way is done again.
  - Not a background `URLSession`: iOS treats every task an app creates
    while in the background as discretionary (it may wait for Wi-Fi and
    power) and wakes the app between tasks with growing delays, so a piece
    at a time would crawl or stop on cellular, and one task for the whole
    remainder would give up the pieces (and need a copy of the rest of the
    file). An app iOS ends while suspended loses its composer, as before;
    its upload on the server lapses after `idleTimeoutSecs`.
- **Audio files.** The Files picker takes `.audio` types too (mp3, m4a, aac,
  wav, flac, aif, aiff, caf, ogg, opus, …). An audio file is an
  `AttachmentUpload` of kind `.audio`: never compressed, refused over
  `maxMediaBytes` (20 MiB on an older server), uploaded the same way, its
  type from the extension (`audio/mpeg`, `audio/mp4`, `audio/wav`, …). Its
  chip is a waveform with its length; the message's `resource_link` becomes
  the inline audio card, which streams from fork.190 on.
- **Is it there, in one request.** `MediaPresence` asks `stat_paths {paths,
  rootPaths}` about every queued path, up to 200 paths and 32 roots a
  request. A path's roots are the session's folder, the home when the path
  is in it, and the `cd` a printed relative name was joined to
  (`MediaRef.base`); codeg adds its uploads directory itself. An answer
  `allowed`, `exists` and `isFile` is there with its size; `exists: false`
  or a directory is missing; an `error` leaves the card to find out
  (`unverified`), as does `invalidPath`. A path `outsideRoots` or
  `symlinkEscape` (an absolute path elsewhere, a link out of the folder) has
  its directory listed as in 1.3.14, so `/tmp/render/cut.mp4` still shows.
  A 404, 405 or 501 means a server without `stat_paths`: listings from then
  on; any other failure lists that batch. Hidden files are now checked too
  (a listing leaves out dotfiles).
- **Checked live** (on macOS, with the app's own `ResumableTransfer` and
  `CodegClient` built into a small command-line harness, against codeg
  fork.203): `upload_limits` answered 1 GiB for video and audio, resumable,
  8 MiB pieces suggested. A 6 MiB file sent in 2 MiB pieces through a proxy
  that cut the connection 3 MiB in, in the middle of the second piece:
  the transfer waited, asked `upload_attachment_status`, which held
  3,144,868 bytes (what had landed of the cut piece, less the requests'
  headers), went on from there rather than from the piece's start or from
  zero, and completed; the stored file's SHA-256 matched the original.

#### Usage limits and the account pool

`LimitReason`, `LimitPause.reason`, `SessionActivity.limitPaused` and
`.limitStopped` (`Models/`), `LimitPausedBanner`
(`Features/SessionDetail/SessionActivityViews.swift`),
`Networking/CodegClient+LimitContinue.swift`, `SendFailure.poolExhausted`
(`Features/SessionDetail/Outbox.swift`). Mirrors codeg web's
`limit-pause.tsx`, `lib/limit-continue.ts` and the `pool_wait` attach phase.

- **Why it waits.** A conversation's `limit_reason` is `usage_limit` (the
  account's own limit) or `pool_capacity` (the local account pool, maxpool,
  answered 429: every account behind it is at its limit). A pool pause reads
  "Paused by usage limits — continues at 14:30" under the session's title
  and "Paused · continues 14:30" on its row (VoiceOver: "Paused by usage
  limits, continues at 14:30"), with the hint "Every Claude account behind
  the account pool is at its limit. This session continues by itself once
  one frees up." The time is the pause's `resets_at`, for the pool when its
  first account frees up. A pause from a server without `limit_reason` reads
  as the account's own limit, as before.
- **Stopped.** A turn interrupted on a usage limit whose pause ended without
  continuing (the continuations met the limit three times and gave up, or
  were cancelled): `limit_reason` set, no `limit_pause`. It reads "Stopped by
  usage limits" ("Stopped by limits" on the row) and offers Continue.
- **Cancel auto-continue and Continue now.** Above the message bar a paused
  session shows "Paused by usage limits" (or "Paused on the usage limit")
  and "Continues automatically when it resets at 14:30 (in 2h 5m).", with
  Cancel auto-continue (`POST /api/cancel_limit_continue {conversationId}`:
  the pause ends and the turn stays interrupted, with Continue) and Continue
  now (`POST /api/continue_limit_now`: the continuation goes out at once and
  may meet the limit again, which pauses it again). Once the continuation is
  claimed only "The limit has reset — continuing now." remains. Cancel shows
  at once and is put back if the server refuses; each reads the
  conversation again afterwards (Continue now after a few seconds).
- **Opening a session while the pool is full.** The `attach_progress` phase
  `pool_wait` comes with `pool_resumes_at` (epoch seconds); the title line
  reads "Connecting… (all Claude subscriptions are at their limit — the
  next one frees at 14:30)", without the time when the pool doesn't know it.
- **A message the pool holds back.** codeg refuses a prompt with 409
  `pool_exhausted` ("All Claude subscriptions behind the account pool are at
  their limit, so Claude Code cannot take a request yet; the next one frees
  at 14:30 UTC. [pool_exhausted resumes_at=N]"). The app read every 409 as
  "a turn is already running" and waited for a turn that wasn't running.
  Now `CodegClient` keeps it a server error (`APIError.isPoolExhausted`,
  `poolResumesAt`), and the message stays at the front of the queue, "Not
  sent · All accounts at their limit — will resend at 14:30", going again by
  itself five seconds after that time (every minute when it isn't known),
  however many times it meets the limit.

`CodegiOSTests/SessionActivityTests.swift` covers both continuation
wordings; `DictationRefineTests` the kept answer and its decoding;
`SessionForkTests` Pi and the server's word, in the rules and through the
forker; `LimitPauseTests` the pool pause, the stop, the two actions on the
wire, `pool_wait` and a prompt the pool held back.

### Through connection drops and offline (1.3.23)

Phase 1 of the offline plan on the phone (items 1.5 and 1.6), next to the
desktop and web half on `fork/solution-plan` (the status pill, the resync
coordinator, adaptive pong deadlines). The wording and the timings follow
codeg web's `src/lib/connection-display.ts` and
`src/lib/transport/liveness.ts`.

#### Lists saved for a start without a network

`Persistence/ServerSnapshotCache.swift`.

- **What.** After every load that brought the conversation list,
  `ActivityModel` and `SessionListViewModel` save the lists
  `ServerSnapshotLoad` gave: all folders, the open folders, the
  conversation summaries, the folder groups and the attention snapshot.
  One file per server, `lists.json`, in the server's folder of the
  transcript cache (`Caches/TranscriptCache/<serverKey>/`), so removing a
  server or changing its URL or token removes its lists with its
  transcripts. The transcript cache's eviction leaves the file alone.
- **When it shows.** A list with nothing loaded yet shows the saved copy at
  once, then asks the server. The copy's date is the file's modification
  date: Activity's "Updated …" line shows it, Chats shows "Last updated
  14:02" (with the day when it isn't today) while it shows the saved copy
  or the link is offline, and the capsule says "Offline · updated 3 min
  ago".
- **Writes.** The 25-second pulse brings the lists again and again; when
  they didn't change (a SHA-256 of the encoded lists) only the file's date
  moves. Capped at 2 MB: larger lists are saved without their least
  recently updated sessions, pinned ones last.
- **No network.** While the phone has none (`ConnectivityMonitor`), the
  pulse and Chats don't ask the server, since a request would only wait
  for connectivity. The pulse waits for the network and refreshes the
  moment it is back; Chats reloads then if it shows its saved copy. With
  nothing saved the screen says "You're offline. The sessions show here
  once the phone is back online."
- **Saved sessions.** Transcripts were already kept (`TranscriptCache`,
  1.3.6), so a saved session opens offline as before; the capsule's age
  there is when the screen last heard from the server.

#### File protection

`ProtectedFiles` in `ServerSnapshotCache.swift`. The lists and the
transcripts are written with `.completeFileProtection`, and their folders
are made with `FileProtectionType.complete`: iOS keeps them unreadable from
about 10 s after the phone locks until it is unlocked. A simulator doesn't
apply protection, so CI checks that every saved file goes through this
store (a recording `SavedFileStore`); the check of the protection itself
runs on a device. What an earlier version saved
gets the protection on the first read or write of each launch (a locked
phone refuses; the next launch tries again). Nothing reads these files
while the phone is locked: the app has no background tasks, and read-aloud
speaks from memory. A read that fails while locked is a miss, never a
deletion. `MediaDiskCache` and the outbox keep the default protection:
session audio may play from the media cache with the screen locked, and
the outbox must stay writable when a send fails in the background.

#### The connection capsule

`App/LinkStatus.swift` and `DesignSystem/ConnectionCapsule.swift`, on
Chats, Folders, Activity and the session screen.

- **States.** "Reconnecting…" after 1 s of the server out of reach with
  the app in front; "Offline · updated 3 min ago" after 10 s, or after 1 s
  without any network; "Updating…" while the first refresh after an outage
  runs; "Back online" for 2 s. Down time counts only while the app is in
  front. Unlike the web, no network also waits that first second, since a
  switch from Wi-Fi to LTE can report none for a moment.
- **Inputs.** The network path, the list pulse (a refresh that couldn't
  reach the server; a server that answered with an error is up, and its
  error keeps the banner), and the session screens' sockets while they
  reconnect.
- **Never in the way.** A capsule over the top of the content, under the
  navigation bar, that takes no taps. A list that can't be refreshed keeps
  its rows; the refresh-error banner is for the other errors.

#### Network monitor

`Networking/ConnectivityMonitor.swift`: `NWPathMonitor` reduced to online
or offline and the kinds of interface in use. `.requiresConnection` counts
as online, and so does the unknown state before the first report, so
nothing is held back at launch. Its events: went offline, came online, and
path changed (still online, over another kind of interface).

#### The event socket's pong deadline

`Networking/StreamLiveness.swift` (pure), driven by `EventStream`:

- a ping after 5 s of quiet while a turn streams on screen, 20 s
  otherwise;
- the pong is due within `clamp(3 × p95, 8 s, 30 s)`, the p95 over recent
  pong delays and probe durations; any frame settles a ping;
- a late pong triggers `POST /api/health` on a session that doesn't wait
  for connectivity: an answer keeps the socket and extends the deadline
  (twice at most), no answer ends the stream with `.closed`;
- a new socket must hear its ready frame within 10 s, behind the same
  probe, since a connect to a tailnet address whose machine is off can
  hang;
- a network change, or the network back, checks the open socket with a
  4 s deadline instead of dropping it: the Tailscale-tunnelled connection
  often survives a switch.

Before 1.3.23 the ping had no deadline, so a half-open socket lived until
TCP gave up.

#### A running turn through a dead zone

`StreamReconnect` in `StreamRecovery.swift`, and `reconnectStream` in
`SessionDetailViewModel`:

- no reconnect is attempted, or counted, while the phone has no network;
  the network coming back sends one at once;
- with a network: 0.5, 1, 2, 4, 8, 8 s, as before;
- then the server is asked once: a reply that landed meanwhile is adopted,
  a turn the server says ended is settled, and a connection the server let
  go fails the turn as before ("Lost the connection…");
- a server that can't be reached, or that still runs the turn, keeps the
  turn on screen, and the socket tries again every 30 s while the screen is
  open. 1.3.22 failed the turn after about 24 s.

The screen shows the turn as Working throughout, and the capsule shows the
link is down. Leaving the screen, or the app going to the background,
stops the tries; coming back reconnects as before.

### Expired questions, paused and delivered sub-agents (1.3.24)

Follows `fork/solution-plan` at 65fa63990 (the "keep a question open until
it is answered" and "deliver a limit-paused sub-agent's result" work).
Presentation only; no new endpoints.

- **"This question expired".** codeg's `ask_user_question` now stays open
  until it is answered, so a call that ended without an answer can no
  longer be answered. `AskQuestionParse.recordState` ports web
  `askQuestionRecordState` (`src/lib/ask-question.ts`): an error result is
  `error` when codeg-mcp rejected the arguments (`ask_user_question
  requires|supports`, `questions[n]`, `-32602`) and `expired` otherwise; a
  result is `answered`; no result is `inFlight` only while the live turn
  holding the call runs (`ToolCallVM.inRunningTurn`, set by
  `MessageRender.adaptLive` from `LiveTurn.isStreaming`) and `expired`
  after. A transcript's call with no result is never waiting: its turn
  ended, or a reattached live turn stands in for the running one. The card
  says "This question expired" with "The agent stopped waiting before it
  was answered.", the questions' headers and the error's first lines, and
  its rail marker is a quiet grey (`MarkerKind.muted`) instead of a pulse.
  Strings: web `askQuestionResult.expired` / `expiredHint`.
- **Paused sub-agents.** A delegation a usage limit stopped carries
  `error_code: "paused_usage_limit"`: with `failed` in the delegate card's
  `meta["codeg.delegation"]` (and the stored history), with `running` in a
  `get_delegation_status` report. `DelegationModel.isPaused` turns both
  into `paused` (`DelegationCardStatus`, `BadgeStatus`), and the badge
  reads "Paused · usage limit" in amber with a pause glyph (web
  `delegation.status.paused`). Paused is never sticky: the card follows the
  latest meta and a status row its latest poll, so `completed` reads Done.
  On the phone the delegate card's meta changes when the transcript reloads
  (after the delivery turn, or on opening the session): the app does not
  handle the live `delegation_completed` event.
- **Delivered results.** When a continued sub-agent finishes, codeg sends
  its result to the parent as a user message (`limit_delivery::
  delivery_prompt`): a note to the agent, then `<delegation-result
  task_id="…" agent="claude_code" status="completed" [error_code="…"]
  child_session="42">…</delegation-result>`, ending the message.
  `DelegatedResult.parse` reads a text-only user turn that ends with the
  block (the first opening tag, the last closing tag, so a result quoting
  the tag survives), and the timeline draws it as `DelegatedResultCard`
  instead of a message: the agent, `#task`, the status badge, "Sub-agent
  result", three lines of the result and "Open the sub-agent's session",
  which pushes the child conversation (`SessionActions.openSession`).

`CodegiOSTests/ServerStatesTests.swift` covers the record states, a
transcript's and a live turn's unanswered question and their markers, the
paused delegate card, delegate output and status rows turning Done, the
badge, and reading delivered results (and what is not one).

### Attaching documents (1.3.25)

`Features/SessionDetail/DocumentAttachment.swift` (`PickedFileRoute`,
`AttachmentKind`, `DocumentAttachmentPrep`, `DocumentAttachmentError`),
`Features/SessionDetail/VideoAttachment.swift` (the job's `.document` kind),
`Features/SessionDetail/AttachmentChipsView.swift` (`DocumentAttachmentChip`),
`Models/MediaReference.swift` (`MediaFormats.attachment(atPath:)`). Until
1.3.24 Files offered only pictures, videos and audio
(`allowedContentTypes: [.image, .movie, .audio]`), so a PDF was greyed out.
Nothing changed on the codeg side: `upload_attachment` and the resumable
upload already take any file, up to `max_file_bytes` when it isn't video or
audio (`UploadLimits::limit_for`).

- **What Files offers.** `[.image, .movie, .audio, .pdf, .data]`: any
  regular file (PDF, Word, text and Markdown, CSV, spreadsheets, code,
  archives…). A folder or a package isn't `public.data`, so it stays greyed
  out; one that comes through anyway (`isDirectory`, `isPackage`, read
  inside the picker's security scope) says so in the composer's notice
  ("Projects is a folder. Attach the files in it instead.", "Deck.key is a
  package, not a single file, so it can't be attached.") instead of failing
  silently.
- **Where each file goes** (`PickedFileRoute.route(forFileNamed:)`, by the
  name's type):
  - a `public.image` is a picture and rides in the prompt as before
    (downscaled, re-encoded when it must be); one the iPhone can't decode
    (an SVG, say) goes as a document instead of "Some images couldn't be
    added";
  - video and audio follow the app's own media table (`MediaFormats`, the
    formats the transcript plays), then the system's type (`.movie`,
    `.audio`), and keep the path of 1.3.22 unchanged: compression, Original
    or Compressed, the media limit;
  - everything else is a document. `.ts`, `.mts` and `.cts` are TypeScript,
    not an MPEG transport stream: the iPhone types them as video, which a
    server before fork.191 would refuse as "no video in it".
- **The job.** A document is an `AttachmentUpload` of kind `.document`, on
  the machinery of video and audio: copied into the app's own folder (inside
  the security scope), the server's limits asked (`upload_limits`, cached),
  uploaded as it is, never compressed, in pieces
  (`upload_attachment_create`, `chunk`, `complete`) on a server that takes
  the resumable upload and in one multipart `upload_attachment` otherwise,
  with the same retries, pause in the background, Try Again and cancel on
  removal. The copy is deleted once the server has the file.
- **Its type.** `DocumentAttachmentPrep.mimeType(forFileNamed:)`: codeg web's
  type for the names it knows (`MIME_BY_EXT` in
  `src/components/chat/composer/attachment-files.ts`: `text/markdown`,
  `text/csv`, `application/json`, `text/typescript`, …), the office formats
  and `application/zip`, then the system's (`UTType.preferredMIMEType`),
  `text/plain` for text without one, `application/octet-stream` for the
  rest. It is the multipart part's `Content-Type` and the create's
  `mimeType`; codeg records it and answers it back. `Attachment.mimeType` is
  now the real type for every kind (it was `video/mp4` or `audio/mpeg`
  whatever the file).
- **Size.** Checked before a byte is sent, against the server's
  `maxFileBytes` (20 MiB, and 20 MiB from a server that doesn't report its
  limits). A document over it is refused with a notice, "Report.pdf is
  23 MB; codeg takes documents up to 20 MB." (both in binary megabytes, as
  codeg counts its limits; "is over 20 MB" when the two would read the
  same), and its chip goes: Try Again couldn't help. The server's own
  refusal (`errors.upload.tooLarge` with its `limit`, or a 413) reads the
  same way, and so does an empty file ("notes.txt is empty, so it wasn't
  attached.", which codeg refuses too). Any other failure (the network, the
  upload space full) keeps the chip, outlined red, with Try Again, as for a
  video.
- **The prompt.** The `resource_link` of video and audio:
  `{type: "resource_link", uri: "file://…", name, mime_type}`, with the type
  the server recorded (the name's when it recorded none). That is codeg's
  `PromptInputBlock::ResourceLink`; its `description` is optional, and codeg
  web sends it as null. The agent gets an ACP resource link to the file under
  codeg's uploads directory and reads it with its own tools. Send, insert
  and queue wait until every upload is done:
  "Wait for the document to finish uploading.", "A document didn't upload.
  Tap it to try again, or remove it."
- **The chip.** `DocumentAttachmentChip`, 176 by 56 pt beside the 56 pt
  pictures and videos: the document's symbol (`doc.richtext` for a PDF,
  `doc` otherwise, as its card in the message has it), its name, truncated in
  the middle, and under it its size and type ("PDF · 2.3 MB"), how far the
  upload is ("40% · 2.3 MB"), "Waiting for the network", "Paused" or "Didn't
  upload". A ring stands in for the symbol while it uploads. A tap on a
  failed one says why, with Try Again and Remove; the corner's ✕ and the long
  press remove it; VoiceOver reads its name and where it is ("PDF document,
  2.3 MB").
- **In the message.** The optimistic message carries the link codeg shows
  for the attachment (`[Report.pdf](file://…)`), and codeg's history
  projects the `resource_link` the same way (`attachment_marker`). A PDF or
  an office file was already a document card (`MediaFormats.documents`
  since 1.3.13: its name, "PDF document", Quick Look on a tap). Any other
  file now is too, in the user's own message only and only for a `file://`
  link into codeg's uploads directory (`…/uploads/<bucket>/<name>`, where
  `upload_attachment` puts it): `MediaFormats.attachment(atPath:)`. A file a
  message merely mentions (an `@`-mention from the desktop or web composer,
  `[main.swift](file:///…/proj/main.swift)`) stays a link in its text, and an
  agent's reply shows what it showed before. Several attachments fold into
  one row ("1 PDF · 1 document").
- **Strings.** In the string catalog with zh-Hans: the notices, "The
  document didn't upload", "Didn't upload", "Waiting for the network",
  "Paused" and "Document".
- **Tests.** `CodegiOSTests/DocumentAttachmentTests.swift`: the routing (a
  PDF, office, text and code files, an archive and a name without an
  extension to the document upload, pictures inline, video and audio to
  their uploads, a folder), the types, the size notice (the 23 MB example,
  the "over" case, an empty file), the limit with and without
  `upload_limits`, the server's too-large answer on both paths, the
  resumable and the multipart upload byte for byte, the exact
  `resource_link` in `acp_prompt`, a send that waits for the upload, a
  failure that keeps its chip and goes on with Try Again, the oversized
  document whose chip goes, and the cards in the message.
- **Checked live** with curl, as the app sends it, against an isolated
  codeg-server (fork.204 from the app bundle, with a HOME, data directory
  and `CODEG_HOME` of its own on port 3397; never the live server):
  `upload_limits` answered 20 MiB for files and 1 GiB for media; a 3 MB
  `Report.pdf` created as `application/pdf` was admitted under the 20 MiB
  limit, went up in two pieces and completed to
  `uploads/<bucket>/Report.pdf` with `mimeType: application/pdf` and the same
  SHA-256; `Notes.md` (`text/markdown`) and `app.ts` (`text/typescript`) went
  in one multipart request each; a create of 23 MiB answered 500
  `errors.upload.tooLarge` with `limit` 20971520, and an empty one 400
  "Uploaded file is empty". `stat_paths` found the uploaded file under the
  uploads root as configured (`/tmp/…`), and said `outsideRoots` for the
  canonical path the upload answers (`/private/tmp/…`); the app then lists
  the directory instead. Only an uploads root under a symlink differs so.

## Session lists

The Chats folder cards, a folder's full list, Activity and Search share one
row, `Features/Sessions/SessionRow.swift`. Upstream drew each session as one
line of small text with no separation, so sessions were hard to tell apart and
it was unclear which one a tap had opened.

- **Row.** The agent's avatar (with the review-status dot), the title in
  headline type on up to two lines, and the relative time on the right. Below
  it, the agent, the folder, and a status tag when the session is doing
  something: Working, Needs you, Interrupted, Paused (with the reset time),
  Continuing. An idle session shows no tag. The fork has no last-message text
  on a summary, so there is no preview line.
- **Surface.** In Activity, Search and a folder's full list each row is a flat
  card (`Theme.bgElevated`, a hairline, `Theme.Radius.md` corners, 8 pt apart).
  Flat rather than Liquid Glass: a glass plate per row reads as a stack of
  shadowed plates on the light backdrop and costs a backdrop pass per cell.
  Inside a Chats folder card (which is glass) rows stay inset, between inset
  dividers, like the grouped Settings rows.
- **Touch.** A press highlights the row's surface (`Theme.pressed`) and shrinks
  it slightly. In a Chats folder card a row opens its own session; the header
  and "Show all" open the full list (upstream zoomed the whole card open on any
  tap). Since 1.3.6 the full list is pushed (`Route.sessionGroup`, with the
  same zoom), not presented over the tabs, so Back from a session opened in it
  returns to it. A long press offers Open, Fork Session, Pin/Unpin, Copy
  Title and Archive Folder (1.3.11, see "Forking a session").
- **The session you came from.** `AppModel.lastOpenedConversationID` records
  the conversation opened last, from a list, a link or a notification. On
  iPhone every list draws that row with an accent outline; on iPad the lists
  mark the session open in the detail column.
- **Accessibility.** VoiceOver reads a row as one element: title, status,
  agent, folder and the time in words (`RelativeTime.spoken`), with Fork
  Session and Pin/Unpin as actions and the selected trait on the marked row. The avatar scales
  with Dynamic Type, titles get four lines at accessibility sizes, and the
  details line stacks instead of squeezing.

This part is offered upstream as
[#20](https://github.com/xintaofei/codeg-ios/pull/20) (rows, folder cards,
marking; with Running / Review tags instead of the fork's activity states).

### Activity: newest at the bottom (fork only)

Settings › Appearance › Activity › **Newest at the bottom**, on by default
(`AppearanceStore.newestAtBottom`, key `codeg.activity.newestAtBottom`). The
Activity feed is turned over so the most recent session sits at the bottom of

"Running" last, each oldest first, with every header above its own rows
(`ActivityFeedLayout`). The error banner moves to the bottom with the newest

jump, and a short list sits at the bottom), and `.sizeChanges` at the bottom
only while pinned. `BottomPin` follows the transcript's rule (upstream #16):
only the user's own scroll unpins; a refresh, new rows or a layout pass can
only re-pin. While pinned, a session that updates or arrives keeps the newest
row in view; scrolled up, the list stays where it is.

## Rotation, Back, and long sessions (1.3.6)

### Rotation keeps everything

A Plus or Pro Max iPhone reports a regular width in landscape, and
`RootView` picked its shell from the width class: tabs when compact, the
iPad's three-column split view otherwise. Turning the phone swapped one for
the other. Everything under the root was rebuilt: the open session's
`SessionDetailView` disappeared, so its model was torn down (event socket and
presence socket closed); the split view showed no session at all (it reads
`selectedConversationID`, which pushes on iPhone never set); turning back
rebuilt the tab and its stack, so the session loaded and attached again from
scratch, with its scroll position, draft and live turn gone. Activity, Search
and the folder screens lost their scroll positions the same way.

- **One shell per device** (`App/ShellLayout.swift`). An iPhone always gets
  the tabs; in landscape they are wider. Inside the tab shell the width class
  is pinned to compact, so no screen switches layout on a rotation either
  (the Chats list's iPad search field, the screen titles). This was chosen
  over carrying state across the swap because the swap itself was the
  inconsistency: a different app on its side.
- **Session models live above the shells** (`App/SessionModelStore.swift`,
  owned by `AppModel`), keyed by server, endpoint and token, and
  conversation (or draft). A screen holds its model with a `SessionLease`
  between `onAppear` and `onDisappear`. Only when no screen has held it for
  0.7 s is it suspended (its sockets close, as leaving a session always did),
  and a send still being handed to the server finishes first. A suspended
  model keeps its turns and draft, so opening the session again is instant;
  the 6 most recently used are kept, all are dropped on a memory warning or a
  server change. An iPad window resized across the width boundary still
  swaps shells, and `AppModel.setLayout(compact:)` carries the open screen
  across (the sidebar section, content pushes and detail become that tab's
  stack, and back), so the session's screen is rebuilt around the same model.
- **Test.** `RotationTests` hosts the whole `RootView` on the CI simulator
  (an iPhone 17 Pro Max) against a mock server, opens a running session from
  Activity, and turns the simulator to landscape and back twice
  (`requestGeometryUpdate`). It checks the tab shell, the Activity stack, the
  same model, never suspended, the live turn, the draft, one socket never
  closed, and no second transcript fetch. Where the simulator doesn't turn or
  stays compact, it sets the width class a Pro Max reports. Captures:
  `rotation-portrait.png` and `rotation-landscape.png` in the
  `session-list-screenshots` artifact.

### Back returns where you came from

- **From a list.** A session opened from Activity, Search, a folder or a
  Chats card is pushed on that tab's stack, so Back returns to it, with its
  scroll position and filter. This held before, except across a rotation
  (above) and from a Chats folder's full list, which was a full-screen cover
  dismissed on open, so Back landed on the Chats list. That list is now a
  pushed screen.
- **From a notification or a link** (`AppModel.openSessionFromOutside`). Both
  used to open the session on the Chats tab with a fresh stack, so Back went
  to Chats even if you were in Activity. Now the session opens on the tab you
  are on, in place of any session open there, so Back returns to the list,
  folder or search you were looking at; from Settings it opens on Activity.
  The selected tab is remembered across launches (`codeg.lastSelectedTab`),
  so a notification that starts the app opens on the tab you left it on. On
  iPad the session fills the detail column next to the section you were on.

### Opening long sessions

Measured on the box against conversation 86 (a Claude session whose JSONL is
35 MB, with 1,697 turns and 56 pictures), and three bigger ones. Times are
over loopback on the M1 box (no network), median of three, with the app's
own models, window and cache code built for macOS (1.3.5's for "before") and
a plain `URLSession` request in place of `CodegClient`.

| | conv 86 | conv 36 | conv 58 | conv 128 |
| - | - | - | - | - |
| Transcript file | 35 MB | 119 MB | 58 MB | 82 MB |
| Turns | 1,697 | 6,290 | 4,292 | 5,120 |
| Server time (any request) | 0.08–0.14 s | 0.33–0.66 s | 0.50–0.78 s | 0.19–0.25 s |
| **Before**: whole transcript, compressed | 8.7 MB (14.1 MB raw) | 18.5 MB | 7.8 MB | 13.9 MB |
| Before: fetch and decode, no network | 768 ms | 2,910 ms | 1,698 ms | 1,860 ms |
| **First open now**: latest 120 turns, compressed | 1.0 MB | 2.2 MB | 0.3 MB | 2.1 MB |
| First open now: fetch and decode, no network | 131 ms | 474 ms | 562 ms | 317 ms |
| **Cached open**: on screen from disk | 6 ms | 14 ms | 3 ms | 12 ms |
| Cached open: background refresh, compressed | 130 KB | 12 KB | 57 KB | 22 KB |
| Cached open: background refresh time | 80 ms | 342 ms | 521 ms | 192 ms |

Over the phone's network the transfer comes on top: at 20 Mbps the old
8.7 MB for conversation 86 took about 3.5 s more (18.5 MB for conversation
36, 7.4 s), the first open now about 0.4 s, a cached open nothing before it
draws. Of the client's own time, decoding the whole of conversation 86 took
306 ms on the M1 (1,037 ms for conversation 36) plus 47 ms re-reading the
JSON for the selector state; 120 turns take 14 ms. Rendering was already
limited to the latest 50 turns; its pictures now decode off the main thread.

What changed:

- **Windows** (`Features/SessionDetail/TranscriptWindow.swift`). codeg
  serializes a window of a transcript on request (`tailTurns`, `fromIndex`)
  with `turns_offset`, `turns_total` and `prefix_hash`, the server's FNV-1a
  fingerprint of the turns before the window (`turn_window.rs`); the web
  client uses it. A session now opens with its latest 120 turns, from a user
  turn. "Show earlier messages", or scrolling near the top, fetches the 150
  turns before them (`get_folder_conversation_turns`), joined only when the
  page's `prefix_hash_before_index` equals the window's fingerprint. Every
  refresh (reopening, the app returning, a turn finishing, a reconcile) asks
  only `fromIndex` = the held end minus an overlap (40 turns when reopening
  or returning, which the server may have rewritten in place; 8 after a turn
  on screen), and checks the response's `prefix_hash` against the held
  window's fingerprint extended over the held turns
  (`TranscriptFingerprint`, the server's function, computed from each turn's
  exact `timestamp_millis`). A response that doesn't join means the history
  was rewritten (a compaction), and the screen starts over from a fresh
  window. A response that joins but ends before the screen is a stale read
  and never takes turns away. A turn only the phone has (a reply that was
  never reconciled) is never part of a fingerprint and is fetched again. A
  server without windows answers with the whole transcript, used as before.
  Each turn keeps the server's exact milliseconds (`MessageTurn.serverMillis`,
  read by `TranscriptTime`, which also replaced the locked
  `ISO8601DateFormatter` for turn times: decoding conversation 86 whole went
  from 300 to 170 ms).
- **Cache** (`Persistence/TranscriptCache.swift`). Each opened conversation's
  window (its server turns, summary, selector state, stats, folder, offset
  and fingerprint) is written to `Caches/TranscriptCache/<server>/<id>.json`
  0.4 s after the last change, off the main thread. `<server>` is a SHA-256
  of the URL and token, so a changed URL or token starts empty, and folders
  of servers that are gone or changed are deleted when the servers change
  (never while the Keychain can't give a token). The cache is capped at
  256 MB, least recently opened removed first (to 80%). Opening a session
  draws the cached window at once, then refreshes as above; the change
  marker is the window's fingerprint and length, checked by the server on
  every refresh. Pictures are stored inside the window, so a cached session
  never fetches them. If the server can't be reached, the cached copy stays
  on screen.
- **Prefetch** (`Persistence/TranscriptPrefetcher.swift`). After each
  Activity refresh, sessions shown there that just finished a turn (no
  longer running, and updated since the last refresh or running then) are
  refreshed into the cache in the background, up to 4 per refresh: a cached
  one gets only what changed (a few KB), one never opened gets its latest
  turns, but only on Wi-Fi (a session that iOS refuses on cellular, a
  hotspot or Low Data Mode) and only from a server that has answered with
  windows. The session on screen is skipped.
- **Pictures** (`Features/SessionDetail/TranscriptImages.swift`). Decoded off
  the main thread with ImageIO's thumbnail path, at most 1,600 pixels on the
  long side, fully (not at first draw, which happened on the main thread at
  full size), and kept in a 96 MB memory cache under a key that is cheap to
  compare (length and both ends of the base64, not the whole string).
- **Title at once.** A session opened from a list shows the list's title,
  agent and status while its transcript loads.

### What the codeg server should change

Once the transfer is small, the server's own time is what remains, and it is
paid on every request, windows included: `get_folder_conversation` parses the
whole JSONL each time (0.08 s for 35 MB, 0.33–0.78 s for the 58–119 MB
sessions above; `parsers/summary_cache.rs` caches only summaries). The iOS app
now asks after every finished turn and on every return to a session, and the
web client does the same. Suggested, in order:

1. **Cache the parsed detail per transcript file**, keyed by path, size and
   mtime (the summary cache's fingerprint), holding the post-processed turn
   list. A hit only slices and serializes the window: a refresh of
   conversation 58 would go from about 0.5 s to a few milliseconds of server
   time.
2. **Parse incrementally.** The JSONL only grows; `transcript_watermark`
   already records the bytes consumed. Resuming from the watermark when the
   file grew (and the prefix is unchanged) would make a miss after an append
   cost only the new lines.
3. Optionally, `fromIndex` with `If-None-Match` on `turns_total` +
   `transcript_watermark` + the prefix hash, answering 304 when nothing
   changed.

## Voice typing (on-device whisper)

The mic in the message bar transcribes speech on the iPhone. The audio never
leaves the phone, and Apple's `SFSpeechRecognizer` is not used, so the app
needs only `NSMicrophoneUsageDescription`. Only when clean-up or translation
is turned on does the transcribed text go to the codeg server (see below).

### Engine: whisper.cpp

`Packages/WhisperCpp` is a binary target for the official whisper.cpp v1.9.1
XCFramework (MIT), pinned by URL and checksum. It is a dynamic framework that
the app binary loads, so `scripts/archive.sh` keeps it in the bundle. The app
uses it with `import whisper`. Everything goes through the `SpeechToText`
protocol (`Features/Dictation/SpeechToText.swift`), and `WhisperCppEngine` is
the only implementation, so the engine can be replaced later.

Why not WhisperKit: it needs ivrit.ai's model converted to Core ML with
`whisperkittools` (PyTorch and coremltools on a large model). That is not
practical on the 16 GB build box, which has no Xcode. whisper.cpp reads
ivrit.ai's published ggml weights directly, and Speakly already uses the same
model, VAD and settings on the Mac. The tradeoff is speed. WhisperKit runs
large-v3-turbo on the Neural Engine at about 6–9× real time on an iPhone 16/17
Pro. whisper.cpp runs on the GPU through Metal, and nobody has benchmarked it
on an iPhone. The XCFramework is built with Core ML support
(`WHISPER : COREML = 1`). A future `ggml-ivrit-large-v3-turbo-q8_0-encoder.mlmodelc`
placed next to the weights would move the encoder to the Neural Engine without
changing the engine code, but producing that file needs the same Python
conversion as WhisperKit.

Decode settings follow Speakly: greedy decoding (`best_of` 1), the language
forced, `no_context`, `suppress_nst`, flash attention, up to 4 CPU threads,
Metal on a device and the CPU in the simulator. Timestamp tokens stay on, as in
Speakly and whisper-cli. With them off, English speech came out transliterated
or translated into Hebrew. Speakly's scaled `audio_ctx` (encode only the length
of the clip) was measured and rejected: it cut decode time by 28% but raised
FLEURS WER from 23.7% to 40%.

### Pipeline

1. **Record.** `DictationRecorder` uses `AVAudioEngine` and converts the input
   to 16 kHz mono Float32. The meter shows input level from -55 to 0 dBFS, and
   a recording stops at 5 minutes.
2. **Trim.** Silero VAD v5.1.2 (the ggml model, through whisper.cpp's VAD API,
   on the CPU) gives one speech probability per 32 ms frame. `VADGate` is a
   port of Speakly's gate (`crates/engine/src/vad/gate.rs`):
   - a segment opens at p ≥ 0.6 held for 2 frames;
   - it closes after 300 ms below 0.35;
   - speech shorter than 250 ms is dropped;
   - a segment is force-split at 25 s.

   `DictationTrim.plan` keeps everything from the first to the last speech,
   with 300 ms of padding before it and 150 ms after (Speakly pads 150 ms on
   both sides; the gate opens only once speech is clear, and a soft first
   syllable was being cut). A recording shorter than 0.4 s is a mis-tap. With
   no speech, or less than 250 ms, nothing is decoded, which avoids whisper's
   hallucinations on silence. If the VAD model fails to load, the whole
   recording is decoded.
3. **Language.** With "Hebrew or English" (the default), whisper tiny tells
   the two apart on the trimmed audio first, leaning to Hebrew (see "Hebrew
   or English" below). The strip's chip can fix it to Hebrew or English for
   the message instead.
4. **Decode.** There is one decode over the trimmed audio, as in Speakly's
   dictation, with the language forced. Output that is only non-speech
   markers (`[BLANK_AUDIO]`, `(מוזיקה)`) is dropped.
5. **Clean up.** With "After transcribing" set to clean up or translate, the
   text goes to the codeg server first (see "Clean-up and translation"
   below). On any failure the words are kept as spoken.
6. **Insert.** `DictationText.insert` puts the text at the field's cursor, or
   replaces the selection, using the iOS 18 `TextField(text:selection:)`
   binding. It adds a space where the transcript would touch a word, and the
   cursor ends after the inserted text. With "Send" on, the message is then
   sent. While a turn runs, it is delivered at once when the turn is held only
   for background work, and queued otherwise.

The model starts loading when recording starts, so the load overlaps the
speech. It is unloaded after 3 minutes idle, on a memory warning, and when the
app goes to the background. A loaded q8_0 model takes about 1.1 GB. iOS doesn't
let a background app use the GPU. If the app goes to the background during a
recording, the recording ends and its decode waits until the app is active
again. A decode that is already running is cancelled and run again then.

### UX

- **Mic button**, next to Send. Tap to start and tap again to finish, or hold
  to talk and let go (a press longer than 0.35 s counts as a hold). VoiceOver
  activation toggles. While recording it is the one control that ends the
  recording: filled with the accent, with a paper plane when the message is
  sent right after transcribing and a check mark when it only goes into the
  message bar. Meanwhile Send, and the agent's Stop while a turn runs, are
  dimmed and inactive, so a reach for "stop" can't stop the agent. While
  transcribing, the mic shows a spinner. It keeps one button style in every
  state, with the fill drawn in its label (anything drawn outside a glass
  button renders under the glass), because swapping styles would replace the
  view under a finger that is holding to talk.
- **Recording strip** above the field, in two rows. The first row says what
  is happening: a pulsing dot, the elapsed time (monospaced, never wraps), a
  level meter of thin bars filling the rest, and cancel (✕); a shutter glyph marks a
  Camera Control recording. While transcribing it shows a spinner and
  "Transcribing…", "Cleaning up…" or "Translating…". The second row holds the
  chips, which wrap onto another line at large text sizes (`FlowLayout`):
  - the language for this message (Auto, עב, EN), filled when it differs
    from the setting;
  - After transcribing (As spoken, Clean up, To English), filled when it
    cleans up or translates. This chip is the setting itself: picking "To
    English" keeps every later dictation in English until it is changed
    here or in Settings. The language chip stays per message, because a
    sticky English would turn every later Hebrew dictation into English;
  - **Send** (send right after transcribing; remembered for the mic).

  While the server cleans up, "Use as spoken" stops waiting for it.
- **Notices.** A dictation notice ("No speech detected", a microphone error)
  is cleared as soon as a recording starts fine, so an old error never sits
  above a working recording. The queued and inserted boxes above the bar
  follow its side margins (36 pt at rest, 16 pt while typing).
- **Settings › Voice › Voice Typing**: the model download (download, pause,
  resume, delete, progress), Language, After transcribing, "Send right after
  transcribing" and "Use the session context".
- **Without the model**, tapping the mic offers the download (919 MB) and
  points to the mic key on the iOS keyboard, Apple's own dictation. During the
  download, a notice shows the progress. If the microphone is denied, a notice
  says where to allow it.
- **Audio session.** One owner, `AudioSessionOwner`
  (`Features/Voice/AudioSessionOwner.swift`), configures, activates and
  deactivates the app's `AVAudioSession` for its three uses: Camera Control
  standby, a recording, and read aloud (`SystemAudioSession` holds the
  category and options for each). `MicrophoneState` decides what the
  microphone engine needs:
  - a recording that starts while the microphone stands by records from the
    running engine, with no session call at all;
  - one that starts while standby is wanted but down (being retried after an
    interruption) starts the engine as standby, which then carries on;
  - otherwise the recording sets `.playAndRecord` with Bluetooth HFP (AirPods
    work as the microphone) and stops the engine at the end, deactivating
    with `.notifyOthersOnDeactivation`.

  If activation or the engine start fails, the owner deactivates cleanly,
  waits 0.25 s and tries once more. A use can only release the session it
  holds, so read aloud and the microphone can't deactivate each other. An
  error is shown in words with Apple's code, for example "Couldn't start the
  microphone: a call or another app is using the audio (!pri).", and the
  `audio-session` and `dictation` logs carry the NSError domain, code,
  four-character code and iOS's own description.

  Any reply being read aloud is stopped before recording. A call or Siri
  interruption, or a route change that stops the engine, ends the recording
  and transcribes it into the message bar without sending it, even with Send
  on; the engine is then marked stopped, so standby starts it again instead
  of trusting a dead one. Haptics are allowed during recording
  (`setAllowHapticsAndSystemSoundsDuringRecording`), so the press and release
  are felt.

### Clean-up and translation (codeg server)

`Features/Dictation/DictationRefine.swift`. `TranscriptPostProcessor` runs
between transcription and insert, for both the mic and the Camera Control.
The phone calls the codeg server it is connected to through the usual
transport (`POST /api/<command>` with the token). The server passes the text
to the provider set up in codeg Settings on the computer (Groq and similar).

- **Contract.** codeg's `docs/dictation-refine.md`, from server fork.155.
  `get_dictation_refine_settings` answers `{ provider, model, endpoint,
  targetLanguage, refine, translate, instructions, configured, providers:
  [{ id, label, hasKey, defaultModel }], keyError }`. `refine_dictation`
  takes `{ text, refine, translate, targetLanguage, sourceLanguage }` and
  answers `{ text, provider, model, elapsedMs }`. Every name is in
  `DictationRefineWire`. Requests use those keys verbatim (camelCase);
  responses go through the shared snake_case decoder, so either casing
  matches. Errors are codeg's `{ code, message }` with a non-2xx status.
- **Arguments.** Clean up: `refine: true, translate: false,
  targetLanguage: null`. Clean up and translate: `refine: true,
  translate: true, targetLanguage: "English"`, except that a translate-only
  provider (Google Cloud Translation) gets `refine: false`, since asking it
  to clean up is an error. `sourceLanguage` is the dictation language by
  name (`"Hebrew"`, `"English"`), which the server names in its prompt, or
  `null` for Detect automatically.
- **Availability.** Each recording asks `get_dictation_refine_settings` while
  you speak (cached per server, refreshed at most every 10 s; a failure to
  ask is not cached). A server older than fork.155 answers 501
  `not_implemented` (codeg's answer to an unknown command), or 404: that is
  "not available", not an error, and the strip hides its chip.
  `configured: false`, a non-null `keyError` (codeg's key store wouldn't
  open), or a `configuration_missing` error from `refine_dictation` is "not
  set up": the notice says "Set up translation in codeg Settings on your
  computer."
- **Never losing the words.** Any error, an empty answer, or no answer within
  12 seconds inserts the transcript as spoken, with a short notice. Other
  server errors (`authentication_failed`, `configuration_invalid`,
  `network_error`, `task_execution_failed`, `io_error`) show codeg's own
  `message`, which it writes for the user. The timeout doesn't wait for the
  request to wind down. The strip's X while "Translating…" shows inserts the
  words as spoken at once. If Send is on, a message kept as spoken is still
  sent, so nothing said into the Camera Control silently stays behind; the
  notice says it wasn't cleaned up.
- **Timeout.** 12 s, as asked for the phone. The server gives its provider
  10 s and then retries once, so its worst case is about 20 s and its doc
  suggests a 25 s client timeout. A first attempt that times out on the
  server therefore always ends as "kept as spoken" on the phone, which is
  quicker for walkie-talkie use. Change `TranscriptPostProcessor.timeout` if
  the retry should get its chance.
- **UX.** Settings › Voice › Voice Typing › After transcribing: Insert as
  spoken (default), Clean up, or Clean up and translate to English, with the
  selected server's status (provider and model, not set up, the key store
  error, too old, unreachable). The recording strip's chip changes it for
  one message (As spoken → Clean up → English). During the call the strip
  shows "Cleaning up…" or "Translating…".
- **Not yet tested against a live server.** The client is tested with a mock
  transport (`CodegiOSTests/DictationRefineTests.swift`) built to the
  server's doc.

### Hebrew or English

The ivrit.ai model transcribes English well when told it is English (15% WER
on the English clips, about the same as the alternatives below), but it can't
tell which language it hears, and the stock multilingual turbo that can is
574 MB more with clearly weaker Hebrew. So a small multilingual whisper only
picks the language: whisper.cpp's `whisper_lang_auto_detect`, which is the
encoder over one 30 s window and a single decoder step, no transcription
(`WhisperLanguageIdentifier`). Its probabilities for Hebrew and English are
renormalized over the two, and the decision (`SpokenLanguageDecision`) leans
to Hebrew: English only when p(en) ≥ 0.9997. Then the ivrit.ai model decodes
with that language forced. The log line `Language en: p(en) 0.99991 in 35 ms`
(category `dictation`) shows each call.

**Test set** (`scripts/stt-bench/lid-cli.swift` and `lid-score.py`, the app's
own code, VAD-trimmed as in the app): 93 Hebrew clips, the 45 used above
(FLEURS he 25, Carmit 12, and the 8 Hebrew BlueTTS sentences full of code
terms, 3 of which the stock turbo had called English) plus 48 new ones: 16
dictation sentences, many dense with code terms ("תריץ npm install ואז pnpm
build", "מה הבעיה עם ה-TypeScript types ב-API client?") or very short ("כן,
תמשיך", "אוקיי, מעולה"), read by Carmit and by two more BlueTTS voices. And
132 English clips: FLEURS en (25 real speakers), the 5 Samantha and 2 BlueTTS
clips, 10 dictation sentences read by eight `say` voices (US, UK, Irish,
Australian, Indian, and the old Fred and Kathy) and by the two BlueTTS voices,
the nearest thing here to English with a Hebrew accent.

**Only the first 3–5 s?** No. tiny q8_0's worst original Hebrew clip went from
p(en) 0.94 on the whole clip to 0.9975 on the first 5 s and 0.999 on the
first 3 s (BlueTTS b03), and it saves nothing: whisper.cpp always encodes a
30 s window, so a call took 9.7 ms whatever the length. The app gives it the
first 30 s of trimmed speech (`SpokenLanguageDecision.windowSeconds`).

**Latency.** On the M4 Max a call is about 10 ms, against about 370 ms for the
ivrit.ai decode of a short dictation. The model (44 MB) loads in 30 ms, while
you speak, next to the big one. On an iPhone it hasn't been measured; the
tiny encoder is about 1% of the turbo encoder's work, so it should stay in
the tens of milliseconds next to the decode's seconds.

**Fallbacks.** No tiny model on the phone, a failed load or a failed call:
the dictation is Hebrew, as 1.3.0 did. Unit tests: `DictationLanguageTests`.

**Download.** `ggml-tiny-q8_0.bin` is part of the Hebrew model's pack
(`languageID` in `stt-models.json`), so one Download gets both (919 MB). On an
install from 1.3.0, the weights and VAD are already verified by the earlier
download's marker, so dictation keeps working (as Hebrew) while the app
fetches only the 44 MB file, on its own at launch or with the next dictation;
Settings shows "Adding the Hebrew-or-English model" meanwhile
(`ModelPackStore.hasVerified`, `SpeechModelStores.completeIfUpdated`).

  [`models-v1`](https://github.com/Jonathan-Asher/codeg-ios/releases/tag/models-v1)

- **Manifest**: `CodegiOS/Resources/stt-models.json` is the same file as the

- **Download**: `ModelPackStore` (`Features/Voice/ModelPackStore.swift`) is

  which is excluded from backups.
- **New model version**: publish a `models-v2` release, update
  `stt-models.json` in both places and bump nothing else. Files with a new name
  or checksum download again.

## Camera Control to talk

With a session open and the mode on, hold the Camera Control (iPhone 16 and
later), speak, and let go. The recording is transcribed on the iPhone, cleaned
up if that's on, and sent the way the message bar's Send sends: a plain
prompt, delivered into a turn held for background work, or queued while the
agent replies. Code: `Features/Dictation/CameraTalk.swift` (press state
machine, when it may run, settings), `CameraTalkController.swift` (the
capture session) and `CameraTalkViews.swift` (the interaction host, the
indicator, the toolbar switch).

### How iOS delivers the button

The only API with press and release is `AVCaptureEventInteraction` (AVKit,
iOS 17.2), phases `began`, `ended` and `cancelled`. From Apple's
documentation and the WWDC25 session "Enhancing your camera experience with
capture controls":

- Events go only to an app that is in the foreground and has a running
  `AVCaptureSession`. Otherwise a press does its usual thing: the Camera
  Control opens Camera, the volume buttons change the volume.
- The primary event comes from volume down, the Action button and the Camera
  Control (and, from iOS 26, a click on an H2 AirPods stem). The secondary
  event comes from volume up. The event doesn't say which button it was.
- An enabled interaction takes over those buttons. Apple asks apps to
  disable it (`isEnabled = false`) whenever they can't handle the events,
  which gives the buttons back to the system.
- Apple tells App Store apps to use it only for capture. This build goes only
  to Jonathan through TestFlight internal testing, which has no App Review.

### The capture session

It exists only so that iOS delivers the button. Back wide camera, `.low`
preset, 10 fps, one `AVCaptureVideoDataOutput` that drops every frame, no
audio input, and `automaticallyConfiguresApplicationAudioSession = false`, so
it never touches dictation's `.playAndRecord` session. It is configured,
started and stopped on its own serial queue. The green camera dot shows while
it runs.

**Preview: unverified.** Apple documents no preview requirement: "actively
use the camera" is the running session. Camera apps that get the events
render their own view from a video data output, and the known workaround for
the termination below keeps a session with a data output running and installs
the interaction on a hidden view. So the default has no preview layer at all.
This hasn't been tried on a device. If the Camera Control doesn't respond,
Settings › Voice › Camera Control › "Show the camera in the indicator" adds a
22-point live `AVCaptureVideoPreviewLayer` to the indicator, without a new
build.

### When it runs

`CameraTalkGate`: the mode is on, the camera is allowed, the app is active,
and a session's message bar is on screen in an active scene, with the photo
camera (attachments) closed. With several session screens (a pushed session,
iPad windows), the one that appeared last owns it. Leaving the session,
backgrounding, the scene going inactive (Control Center, the app switcher, a
system alert) or turning the mode off stops the session. The interaction is
enabled only while the session runs for that screen; when iOS interrupts the
session (a call, another app's camera, heat) it is disabled and the indicator
says why. The session resumes by itself when the interruption ends.

### Press mapping

`CameraTalkPress`:

| Event | Action |
| ----- | ------ |
| press (`began`) | start recording, with a haptic and the recording strip |
| release (`ended`) after 0.3 s or more | stop, transcribe, clean up, send |
| release before 0.3 s | throw away, "Hold the Camera Control while you speak" |
| `cancelled` | throw away |
| the other button pressed while one is held | throw away; nothing until both are up |

**Volume buttons.** While the mode is on they are talk keys too, and they don't
change the volume. Volume down sends the same primary event as the Camera
Control, so the two can't be told apart. Volume up is the secondary event; it
talks as well rather than doing nothing, and pressing it while holding the
Camera Control is a quick way to throw a recording away. To change the volume,
use Control Center or turn the mode off.

**Sending.** The strip's Send switch starts on for a Camera Control recording,
whatever the mic's Send setting, and switching it off keeps that one message
in the bar. The send is the message bar's Send (`sendFromComposer`): a prompt
when the session is idle, into the turn when it is held open for background
work (the message then shows inside the reply), and queued while the agent
replies. No speech: "No speech detected", nothing sent. Without the speech
model, the press shows the same download prompt as the mic. A press while the
last dictation is still being transcribed shows a notice.

**Interruptions.** If the press can't end normally (the scene goes inactive,
the camera stops, the session closes), the recording is transcribed into the
message bar without being sent, with a notice. The capture session has no
audio, and the mic button keeps working while the camera is interrupted.

### Catching the first words (pre-roll)

In 1.3.0 the recording started on `began`, and starting the microphone (the
category switch from read aloud's `.playback`, `setActive`, the engine) took
long enough that messages arrived starting mid-sentence. Now, while the mode
runs for a session on screen, the microphone stands by:

- `DictationRecorder` keeps the engine running and the last 1.5 s of 16 kHz
  audio in an `AudioRingBuffer`, in memory only. A press starts the
  recording with that audio and carries on live (`RecordingBuffer`), so the
  words said while the press registered are there. A mic-button recording
  doesn't take the pre-roll.
- Standby stops, and the session is deactivated, when the mode goes off, the
  session screen is left, the app goes inactive or to the background, the
  photo camera opens, or the camera is interrupted (`CameraTalkController`
  follows the gate). A call or Siri ends it; it starts again when the
  interruption ends, with up to 5 retries.
- Standby uses `.playAndRecord` with `.defaultToSpeaker`, `.allowBluetoothA2DP`
  and `.mixWithOthers`, so it listens through the iPhone's microphone: AirPods
  stay in high-quality A2DP and other apps' audio keeps playing. A
  mic-button recording without standby still uses AirPods' microphone (HFP).
- Read aloud posts `readAloudWillClaimAudio` before it sets `.playback`, and
  standby steps aside until `readAloudDidReleaseAudio`. A press while a reply
  is read stops it and records without pre-roll, so the reply's audio never
  ends up in the message.
- The VAD trim keeps 300 ms before the first detected speech (was 150 ms).
- Settings › Voice › Camera Control › "Catch the first words (keeps the
  microphone ready)", on by default. The orange microphone dot shows while it
  stands by. Off, a press starts the microphone cold as before, and only the
  `.playAndRecord` category is set ahead when the mode starts.
- The log (`camera-talk`) says `First live audio N ms after the press; M ms of
  pre-roll kept`, which measures the real gap on the phone, and when standby
  starts, stops, or loses the microphone.
- Any recording that starts while standby runs, the mic button's too, records
  from that engine without activating the session again (see "Audio
  session" above); the `dictation` log says `Recording from the standing-by
  microphone`.

### The pill above the message bar

"Hold the Camera Control to talk" shows in full for 4 s when the mode turns
on or a session screen opens with it on (8 s, with "Hold the Camera Control or
a volume button, talk, and let go to send", the first time). It then folds
toward the mic into a small shutter badge on the mic button: the mode is still
on, and the toolbar button turns it off. The pill opens in full again only
while the camera is paused or failed, with the reason. Its ✕ only hides the
pill (folding it into the badge at once, or hiding that pause or failure
report until the status changes); the mode stays on, and only the toolbar
button turns it off. During a recording the strip takes its place.

### Setup and permission

The toolbar's Camera Control button turns the mode on or off for every
session (remembered); its shutter glyph is filled while the mode is on. The first time, an explanation comes before iOS asks
for the camera. Turning it on also asks for the microphone, so the first
press doesn't stop at a prompt. `NSCameraUsageDescription` mentions the mode.
Settings › Voice › Camera Control has the same switch, "Catch the first
words", the preview switch and a short explanation. The section and the toolbar button are hidden on
devices without a camera (the simulator).

### "Capture Application Requirements Unmet"

SpringBoard terminates an app with "Camera not actively used;
AVCaptureEventInteraction not installed" (Apple forums thread 769024) when the
app was launched through `CameraCaptureIntent` (from the Camera Control,
Control Center or the Lock Screen, with LockedCameraCapture) and doesn't keep
a camera running. Codeg Plus adopts neither `CameraCaptureIntent` nor
LockedCameraCapture, so it can't be launched from the Camera Control and that
watchdog doesn't apply: it is a plain foreground app with a capture session.

### Diagnosing it on the phone

Console.app on a Mac, with the iPhone connected: filter on subsystem
`io.ashurov.codeg`, category `camera-talk` (clean-up logs to
`dictation-refine`, the recording to `dictation`, activations and their
errors to `audio-session`). Logged: the mode on and
off; every session start and stop with the gate's inputs; configuration; the
first camera frame; interruptions with their reason; runtime errors; the
interaction installed, enabled and disabled; every capture event with its
phase and primary or secondary; what each press did; standby starting and
stopping; and the milliseconds from the press to the first live audio.

### "Couldn't start the microphone: Session activation failed" (1.3.1)

Seen above a recording that was running. There is only one recorder, and a
recording that starts while standby runs never activates the session, so the
banner came from an earlier press made while standby was down, when the
recording started the microphone cold: `setActive(true)` for a non-mixable
`.playAndRecord` session with Bluetooth HFP. Standby goes down and comes back
with every scene or app activation change, camera interruption, read-aloud
claim and release, call and route change, and it was retried only 1 s and then
3 s later. iOS refused that cold activation (the code wasn't logged: 1.3.1
showed and logged only "Session activation failed"); the next press found
standby back and recorded from it, and the banner stayed, because only a send
or its ✕ cleared notices. A related bug: when a call or route change stopped
the engine during a recording from standby, the engine stayed marked as
running, so standby never restarted and later recordings heard nothing until
the screen was left. 1.3.2 routes every activation through
`AudioSessionOwner` with one retry after a clean deactivate, starts a
recording as standby when standby is wanted but down, marks a stopped engine
as stopped, clears the banner when a recording starts, and logs the domain,
code and four-character code of any failure.

### The standby crash (1.3.2 to 1.3.19)

Every crash TestFlight collected from 1.3.2 (40) to 1.3.14 (93), eight on
Jonathan's iPhone 17 Pro Max on iOS 27.2, was the same one, and Apple had
symbolicated six of them: `EXC_CRASH (SIGABRT)` from an uncaught Objective-C
exception raised in AVFAudio, called from
`DictationRecorder.runEngine()` at `DictationRecorder.swift:335`, the
`input.installTap(onBus: 0, bufferSize: 2048, format: inputFormat)` line,
inside the first `AudioSessionOwner.acquire(.standby)` attempt, from
`DictationRecorder.startStandby()` via `DictationController.setPreRoll` /
`retryPreRoll` and `CameraTalkController.syncMicrophone()`. No audio thread
was alive in any of them: it was always a cold start of the standby
microphone, right after `setCategory` and `setActive(true)`. The
`ggml_uncaught_exception` frame is whisper.cpp's terminate handler, which
only passes the exception on. TestFlight's crash logs carry no exception
reason (the App Store Connect API returns only the log text).

The recorder kept one `AVAudioEngine` for the app's lifetime. Its input node
holds the formats of the route it last ran on, and read aloud (`.playback`),
a video, a cold recording with AirPods' HFP microphone (16 or 24 kHz) or a
route change since then had moved the hardware to another format; `installTap`
with `outputFormat(forBus: 0)` then didn't match the hardware, and AVFAudio
raises on that. The format guard already in the code (rate and channels above
zero) couldn't see it.

1.3.20:

- Every cold start builds a fresh engine after the session is active, so
  its input node reads the route as it is now. A leftover engine from a stop
  the recorder missed is stopped and its tap removed first.
- `MicrophoneFormatCheck` checks the input before the tap: an input is
  available, both sides of the node have a sample rate and channels, and
  their sample rates agree (the input node converts channels, never the
  rate). Otherwise it throws a plain error and `AudioSessionOwner` retries
  once after a clean deactivate; the standby retries later as before.
- Every AVFAudio call that can raise (`inputNode`, `installTap`,
  `removeTap`, `prepare`/`start`, `stop`, read aloud's `attach`, `connect`,
  `scheduleBuffer` and `play`) runs through `AVFAudioGuard`, an `@try/@catch`
  in Objective-C (`Packages/ExceptionCatcher`, since Swift can't catch an
  `NSException`). A caught exception is logged, reported to the server as a
  `caught_exception` with its name and reason, and shown as "Couldn't start
  the microphone: the audio system refused the request, try again."
- The engine is registered before it starts, so a configuration change
  posted while it starts is matched to it, and an engine stopped by a route
  change before `start()` returns counts as a failed start. A media services
  reset stops the microphone like an interruption.
- The tap drops a buffer whose format differs from the one its converter was
  built for, instead of converting it.
- Read aloud started its player without checking the engine: a route change
  that stopped the engine mid-reply made the next `play()` raise. It now
  starts the engine before scheduling or playing, restarts it after a
  configuration change while reading, and stops cleanly when it won't.

## Crash reports (1.3.20)

The app sends its crash reports to the codeg servers it knows, and nowhere
else; there is no third-party SDK. `CodegiOS/App/Diagnostics/`:

- **MetricKit.** `Diagnostics` subscribes to `MXMetricManager` at launch and
  turns each diagnostic it delivers (crash, hang, CPU exception, disk-write
  exception, slow launch) into a report: the summary (exception type,
  signal, termination reason, the Objective-C exception's name and message
  where iOS gives them, the crashed thread's frames from two above the app's
  own) and the diagnostic's whole JSON, with paths and URL queries cut out.
  Diagnostics already seen are skipped (an FNV-1a digest of the last 200).
- **Uncaught exceptions.** `NSSetUncaughtExceptionHandler` (chained to any
  handler already set) writes the exception's name, reason, call stack
  symbols and return addresses, the app's version and build, the binary's
  UUID and load address and the breadcrumbs to
  `Application Support/Diagnostics/uncaught-exception.json`, synchronously,
  before the abort; the next launch makes it a report.
- **Caught exceptions.** `AVFAudioGuard` reports what it caught (at most 5
  per launch) as `caught_exception`, with the guarded call's name.
- **Breadcrumbs.** `Breadcrumbs` keeps the last 100 app events and writes
  them to disk 0.3 s after each, so a crash keeps them: `app.launch`,
  `app.active`/`background`/`memory_warning`/`thermal`, `screen.tab` and
  `screen.open` (the tab and the kind of screen on top, no ids), `dictation.*`,
  `standby`, `mic.start`/`stop`/`lost`/`format`/`start_failed` (with the
  route as port types and sample rate), `cameraControl` (the mode's state),
  `readAloud.*`, `media.play`, `audio.route` (reason and port types),
  `audio.interruption`, `audio.engine_config_change`,
  `audio.media_services_reset`, `audio.exception` and `network` (Wi-Fi,
  cellular or offline). Details pass through a character filter (ASCII
  letters, digits and `._:-/=,+`), and enum payloads are dropped
  (`Breadcrumbs.caseName`), so no text from a message, a file or a device
  name gets in. A crash report carries the previous launch's trail, a caught
  exception this launch's.
- **Privacy.** Reports hold stack frames, device and OS, the build and the
  breadcrumbs. Free text from the system (an exception's reason, MetricKit's
  strings) goes through `DiagnosticScrubber`: paths become `<path>`, URL
  queries and fragments `?<redacted>`, `token=`/`password=`/`Bearer …` values
  and 40+ character tokens `<redacted>`.
- **Sending.** Reports wait in `Application Support/Diagnostics/pending/`
  (excluded from backup; at most 50 and 8 MB, three weeks) and go out a few
  seconds after launch, after the app becomes active, and after a new one:
  `POST /api/report_client_diagnostic` with `{"report": …}` to every saved
  server. One server answering `{"id": …, "stored": true}` is enough to drop
  it; a server without the endpoint (404) is skipped.
- **The switch.** Settings › About › "Send Crash Reports to Your Server", on
  by default. Off stops all of the above and deletes what is waiting.

### On the codeg server (fork)

`report_client_diagnostic` stores each report as a JSON file in
`<data dir>/client-diagnostics/` (`$CODEG_HOME`, `$CODEG_DATA_DIR`, or
`~/.codeg`), at most 300 files and 32 MiB with the oldest evicted first, a
resend of the same id stored once, and only the kind and size logged.
`list_client_diagnostics` and `get_client_diagnostic` feed Settings › Logs ›
iPhone crash reports on the desktop and web: time, version and build, iOS,
the exception and the top frames, and "Copy report" for the whole JSON.

### Symbolicating

The TestFlight job keeps every upload's dSYMs as the artifact
`dsyms-<version>-<build>` (90 days, the most a public repository allows):
each `.dSYM` zipped, `uuids.txt` from `dwarfdump --uuid`, and
`build-info.txt`. On the box, `~/codeg-e2e/tools/asc/watch-build.sh` pulls it
into `~/codeg-e2e/dsyms/<version>-<build>/` when the run succeeds
(`~/codeg-e2e/tools/fetch-ios-dsyms.sh <run-id>` does it by hand; the newest
12 builds stay). Then:

```sh
~/codeg-e2e/tools/symbolicate-ios-crash.sh report.json    # "Copy report", or a client-diagnostics/*.json
~/codeg-e2e/tools/symbolicate-ios-crash.sh 2026-10-19T1316.crash
```

It finds the dSYM by the binary's UUID (or the version and build) and runs
`atos` over the app's frames: a crash log comes back whole with them
rewritten, a JSON report as its frames with function, file and line.

TestFlight's own crash submissions are pulled into `~/codeg-e2e/crashes/`
every hour by `~/codeg-e2e/tools/pull-testflight-crashes.sh` (LaunchAgent
`com.codeg.testflight-crashes`, through the App Store Connect helper in
`~/codeg-e2e/tools/asc/`), and symbolicated next to the log when the build's
dSYM is on the box.

### Turning on the TestFlight job

1. Create an App Store Connect API key (Users and Access → Integrations →
   Team Keys) with the **Admin** role. Cloud-managed signing has to create
   certificates and profiles, which a lower role cannot.
2. Add three repository secrets:
   - `ASC_KEY_ID`: the key ID;
   - `ASC_ISSUER_ID`: the issuer ID;
   - `ASC_KEY_P8`: the contents of `AuthKey_<ID>.p8`, raw or base64-encoded.
3. Add the CI signing certificate (see below): the secrets `IOS_DEV_CERT_P12`
   (the `.p12`, base64-encoded), `IOS_DEV_CERT_PASSWORD` and
   `IOS_KEYCHAIN_PASSWORD` (any random string), and the variable
   `IOS_DEV_CERT_ID` (the certificate's App Store Connect id).
4. Set the repository variable `TESTFLIGHT_ENABLED` to `true`.
5. Go to Actions → iOS → Run workflow and tick **testflight**. The build number
   defaults to the run number, and the `build_number` input overrides it. Each
   upload needs a build number higher than the last upload for that version.

An ephemeral GitHub-hosted runner starts with no signing identity, and
automatic signing then creates a new Apple Development certificate through the
API key on every run. Ten of them filled the account in October 2026 and
blocked uploads. The job therefore installs one long-lived development
certificate into a temporary keychain before archiving, and xcodebuild reuses
it. Export still signs with Apple's cloud-managed distribution certificate.

- The certificate's private key, `.p12` and password are kept on the remote box
  in `~/.config/codeg-ios/ci-dev-cert/` (mode 600). The key also exists in the
  repository secrets.
- To replace it (for example, when it expires a year after creation): create a
  key and CSR with `openssl`, `POST /v1/certificates` with
  `certificateType: DEVELOPMENT`, build the `.p12`, and update the three secrets
  and `IOS_DEV_CERT_ID`.
- After every upload, `scripts/revoke_stray_certs.py` revokes any other
  "Apple Development: Created via API" certificate, so a regression can't fill
  the account again. Certificates made from Xcode carry the developer's name
  and are left alone.

### Alternative: Jonathan's self-hosted Mac runner

The same job can run on Jonathan's Mac, so the API key never leaves it:

1. Register a runner for this repository on the Mac (Settings → Actions →
   Runners), with an extra label such as `codeg-ios-release`.
2. Keep the key at `~/.appstoreconnect/private_keys/AuthKey_<ID>.p8` on the
   Mac. Store `ASC_KEY_ID` and `ASC_ISSUER_ID` as repository variables; they
   are not secret. No `ASC_KEY_P8` secret is needed.
3. In the `testflight` job:
   - set `runs-on: [self-hosted, macOS, codeg-ios-release]`;
   - read the IDs from `vars.` instead of `secrets.`;
   - replace the "Install the App Store Connect API key" step with
     `echo "ASC_KEY_PATH=$HOME/.appstoreconnect/private_keys/AuthKey_${ASC_KEY_ID}.p8" >> "$GITHUB_ENV"`;
   - drop the final "Remove the API key" step, because it would delete the
     Mac's key.

The development certificate then stays in the Mac's login keychain between
runs. The Mac must have the iOS platform and the Metal toolchain installed for
its Xcode (`xcodebuild -downloadComponent MetalToolchain`). The repository is
public, so the self-hosted label must stay on this manual-dispatch-only job.
Pull requests from forks must never get a self-hosted runner.
